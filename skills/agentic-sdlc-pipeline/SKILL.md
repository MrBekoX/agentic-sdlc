# Skill: agentic-sdlc-pipeline (the full-envelope SDLC orchestrator)

> **Argument:** `/agentic-sdlc-pipeline $ARGUMENTS` — if given, that is the target work; otherwise ask. Match the user's language.

The full-envelope entry point for production-impacting work. agentic-sdlc-pipeline is not the default for every feature, fix, test, or refactor request; use the focused skill unless the user asks for end-to-end implementation or the work needs the whole SDLC envelope. agentic-sdlc-pipeline **runs the whole flow itself**: it owns the envelope (git lifecycle, Spec & Plan phases, doc-verification, scope-lock, quality gates, task-tracking, the `dispatch-strategy` mechanism map), runs Steps 8–13 from the selected work-type core file against the approved spec/plan files, dispatches `security-reviewer` for the security passes, and dispatches `implementation-auditor` for the final audit. It is a **gated, looped, task-tracked** flow: a red gate means go back, not forward.

## Depth contract (proportional — scale rigor to the change)
Every gate is satisfied by the **actual tool call or artifact** named in the runtime invocation contract — the `Skill` or `Agent` call, the validator's exit code, the `spec-plan-draft` `Workflow` (or, in Codex, the embedded author/critic adapter draft) — never by a sentence in the final report asserting it happened. "Security reviewed", "spec drafted", "control done" are prose, not gates. The Spec and Plan phases (steps 4–5) run their full author⇄critic depth with a fresh-context critic where the runtime exposes one; a shallow inline draft is the flagged degraded path, never the equal of the workflow. When a mandated mechanism has nothing to act on in this context, it carries its **one-line deterministic skip note** in its report (the Step-1-symmetric rule) — it is never silently dropped. Scale the envelope, not the evidence standard: Lite Mode still produces the real tool calls for the gates it keeps, and the high-risk surfaces (auth/payment/DB migration/API contract/permissions/user data/token-session/RLS) are always Full.

## Excuse -> check
| Excuse | Check |
|---|---|
| "Security was reviewed." | Show the completed `Agent(security-reviewer)` result — its findings table — for each required pass, or the documented Step 14 skip note. Dispatching the reviewer is not the review; its returned table is. |
| "The tests went red, then green." | Show the TDD evidence file block for each run: the bare command, its exit code and output tail. A run piped into `tail`, followed by `; echo`, or masked by a `true` fallback hides its own exit and proves nothing. |
| "The spec is fine, I drafted it inline." | The `spec-plan-draft` workflow (or the Codex author/critic adapter) ran with a fresh-context critic; an inline draft is the flagged degraded path, not the gate. |
| "Validation passed, I read the artifact." | Manual Read does not replace `validate_artifacts.py`; show the validator's zero exit, or the gate stays red. |
| "Context is clear, I explored manually." | Manual Read/Glob/ls does not replace `detect_context.py`; the transcript needs the detector run or its skip note. |
| "The step doesn't apply, I dropped it." | A skipped mechanism carries its one-line deterministic skip note in its report — dropping it silently is a failed gate, not a no-op. |

## No placeholders
No "reviewed / validated / audited / controlled" prose standing in for the tool call it claims. No gated step marked done while its check is red — a red gate means go back, not forward. No mechanism dropped without its deterministic skip note. No shallow inline spec/plan substituted for the author⇄critic phases, and no `Delegation Degraded` note used to quietly downgrade a gate the runtime actually supports — the note names a genuinely missing tool and the smallest safe fallback, nothing more.

## Skill architecture
**Two branches.** Focused skills are standalone entry points. Inside an `agentic-sdlc-pipeline` run, do not invoke `feature-build`, `root-cause-fix`, `safe-refactor`, `test-authoring`, `security-audit`, or `implementation-control`: Steps 8–13 read the selected work-type core file, the security steps dispatch `security-reviewer`, and the implementation-control gate runs `resolve_work_package.py` and dispatches `implementation-auditor`.

Not invoking them includes not reading their `SKILL.md`: inside a run, a work-type core file is the only part of a focused skill you read. The pipeline's own `Skill` calls are `dispatch-strategy` (once, at kickoff, before Step 1), `completion-claim-gate`, the read-only `git-safety-check` command at Step 16, and the companions below; a focused skill never calls agentic-sdlc-pipeline.

## At kickoff (always)
1. **Mode select.** Full vs **Lite Mode** (see playbook). Lite is **forbidden** for auth / payment / security / DB migration / production bug / API contract / permission-role / user-data / token-session / RLS — those are always Full.
2. **Work type → core file:** note the selected core; you read it at Step 8, after the Plan Review gate. Bug/broken behavior → `bugfix`, `<runtime-root>/skills/root-cause-fix/references/core.md` · new feature/endpoint → `feature`, `<runtime-root>/skills/feature-build/references/core.md` · behavior-preserving restructure → `refactor`, `<runtime-root>/skills/safe-refactor/references/core.md` · test coverage only → `test-only`, `<runtime-root>/skills/test-authoring/references/core.md`.
3. **Create the task list.** On Claude Code use `TaskCreate`, `TaskGet`, `TaskList` and `TaskUpdate` when the session has them (`TodoWrite` only if `CLAUDE_CODE_ENABLE_TASKS=0`; [tools-reference](https://code.claude.com/docs/en/tools-reference), fetched 2026-10-07). On Codex use `update_plan` or the native tracker. Otherwise write an explicit checklist. Mark a step `in_progress` on entry, `completed` only when its gate passes. **Never** complete a gated step while its gate is red. This is how the human follows progress.
4. **Mechanism map.** Within one pipeline run, call `dispatch-strategy` once at kickoff, before Step 1, and reuse that mechanism map for every later heavy, independent, or parallel step. The map assigns main loop / sub-agent / dynamic-workflow / agent-team per step; never run independent work serially in the main loop. The map also covers the selected work type's fan-out parts (per-module characterization, per-area coverage analysis, investigation and verification lenses); RED/GREEN runs stay in the main loop. Its answer does not end the turn — continue with Step 1 and the branch checkpoint in the same turn. Resuming after a Review gate continues the same run: no second dispatch and no focused-skill routing.

## Companion discipline skills (auto-trigger; cross-cutting)
These fire on their own triggers across the flow — invoke them with the `Skill` tool, don't inline their logic:
- **`mind-spark`** — before kickoff/Spec when the request's shape isn't settled: explore intent and get a design approved, then feed the agreed intent into the Spec phase (step 4). Skips already-specified work.
- **`completion-claim-gate`** — the per-claim, same-turn evidence gate in front of every "done / fixed / passing / works" claim (steps 10/13, Finalize) and before commit (step 17). Complements the `implementation-auditor` gate, which audits the whole flow once.
- **`feedback-triage`** — when handling reviewer / PR / CI feedback (e.g. after step 19): verify each item against the code before applying, push back with reasons, no performative agreement. Inside a run, security-reviewer and auditor findings follow the Loop points, not feedback-triage, and its IMPLEMENT step follows the selected work-type core, not `test-authoring` or `root-cause-fix`.

**Context-fit (skip + document — Step-1-symmetric).** Step 1's "no-op when not a git repo" is the model: a mandated mechanism with nothing to act on in this context is **skipped with a one-line note in its report, never silently dropped** — and the skip decision is deterministic, not a guess. The detector is **`python3 "<runtime-root>/scripts/detect_context.py"`** (stdlib, exits 0):
- **Step 3** runs it first and branches on `explore_mode`: `parallel` (≥2 layers) → explore the layers concurrently; `single` → one `context-analyst`; `greenfield_inline` → no existing code, build the Analysis Summary inline (don't spawn a sub-agent with nothing to read).
- **Step 6** uses `--probe deps`: `stdlib_only` → no external API → Context7 fan-out **n/a** (note it; ≠ the quota-out fallback).
- **Step 15** uses `--probe toolchain`: `absent` → quality gates **N/A** (note it).
- **Step 7** goal lock is a **runtime** check: an active runtime goal already in the session → **don't overwrite it**, lock manually or ask.
- **Step 14** (Security #2): skip it only when nothing changed since the last Step 11 result (a no-op Step 12 and no later edit) → record that; any change runs it.
Detail per step → `playbook.md`. The Spec/Plan author⇄critic phases (4–5) are **never** subject to a skip branch.

**Spec & Plan are explicit conversational phases (steps 4–5):** in Claude Code, each runs the `spec-plan-draft` workflow through the `Workflow` tool (`spec-plan-author` drafts ⇄ `spec-plan-critic` adversarially audits → author revises, ≤2 rounds + closing audit) — Spec with `mode:'spec'`, Plan with `mode:'plan'` (the approved spec as its context). Do not call Claude JS `Workflow` on Grok. In Codex, run the same author/critic discipline inside agentic-sdlc-pipeline with a fresh-context critic when available; do not call standalone `spec-authoring` or `plan-authoring`. A human **Review gate** follows each: resolve the returned decision points before moving on. The spec lives at **`docs/agentic-sdlc/specs/<work_id>.md`** and the plan at **`docs/agentic-sdlc/plans/<work_id>.md`** (same work_id; per-package layout below).

**Approval receipt.** Save the spec (and later the plan) with `status: reviewed` and validate it. Set `status: approved` only after the user approves that Review gate — in a later turn or as an `AskUserQuestion` answer — or when the original request explicitly pre-approves the Review gates. Under pre-approval, resolve each decision point by adopting its recommendation and list it in the gate message; a decision point with no recommendation, or whose options change scope or behaviour that the request does not settle, stays unresolved and stops at the gate. A critic contradiction — a `residualCriticNotes` item that names a contradiction or a hard blocker (on Codex: an issue from the critic's last round) — stops at the gate even under pre-approval. If no answer can be obtained, end the turn with a message that names the Spec Review (or Plan Review) gate, the artifact path and the open decision points. Never treat silence or a tool error as approval. Quote any pre-approval text in the gate message. While the spec or plan is `draft` or `reviewed`, make no source or test edit — stop at the gate and ask.

Steps 8–13 then follow **these two files faithfully** — drift becomes a new task appended to the plan file, never a silent diff — and never draft them again.

**Deterministic artifact gate (machine check under the human Review gate):** before each Review gate, run the validator on the saved file — `python3 "<runtime-root>/scripts/validate_artifacts.py" --mode spec --file docs/agentic-sdlc/specs/<work_id>.md` and, for the plan, `--mode plan --file docs/agentic-sdlc/plans/<work_id>.md --spec docs/agentic-sdlc/specs/<work_id>.md --strict`. A non-zero exit (missing section, untestable criterion, an acceptance criterion mapped to no task, a placeholder/secret) **blocks the gate** until fixed. The validator is **structural only** — it cannot tell whether the spec is *about the requested work*. So at the Spec Review gate **also confirm the spec's topic matches the requested task** (a quick human/semantic check): a mis-carried workflow context (see step 4) can yield a structurally-valid but **off-target** spec that the validator would still pass. (`<runtime-root>/scripts/check_all.py` is an optional manual helper that lints every skill's frontmatter the same `key=value`/exit-1 way; CI runs the deterministic gate on Windows and Linux.)

**Work-type core gate (Steps 8–13):** opens once the plan is `approved`; the read of the core selected at kickoff step 2 comes before the first test or source edit. Read `<runtime-root>/skills/<skill>/references/core.md` for the selected work type before Step 8 and run its core steps as Steps 8–13. The core's security step is Step 11 and runs through `Agent(security-reviewer)`; its refactor step is Step 12; its retest is Step 13; a root-cause-fix core "Final Review" is satisfied by Step 16; a feature-build core "Documentation" step runs before Step 14. The core's last step never ends the run: continue with Step 14 in the same turn. Read `playbook.md` (next to this file) before Step 8. Run every test command bare — no `| tail`, no `; echo`, no `|| true` — so its own exit code is the evidence:
- **feature / bugfix:** edit the test first, run it and see a non-zero exit, and only then edit production code; then run it to exit 0.
- **refactor:** a green characterization run before the first edit, and green after each step.
- **test-only:** no lasting production change. Show the test fail under a temporary mutation — reverted before Step 11 and recorded as a MUTATION run, the one allowed exception — or capture a baseline.

Steps 11 and 14 run for every work type; a core whose security step is conditional (safe-refactor) or absent (test-authoring) does not skip them.

Append each run to the TDD evidence file (paths below) as it happens. A test or source edit before the core read, or a RED that never ran, leaves Steps 8–13 red even if later tests pass.

## Git gating (steps 1–2, 17–21)
- **Approval-gated.** Commit / push / PR / merge happen **only on explicit user request** (contract 08). Propose, don't auto-run.
- **No-op when not a git repo.** If there is no repo, skip git steps, say so, and offer `git init`. Never operate destructively on `main`/`master`; work on a `fix/* | feature/* | refactor/* | security/* | chore/*` branch.
- Secrets: mask (`***MASKED***`), report only `file:line` + risk; never commit/log real values.

## Loop points
- **Test fail** → analyze → fix → retest (runtime loop tool or manual Loop Iteration artifact, step 10/13).
- **Security finding** → fix → re-run `Agent(security-reviewer)` → retest (steps 11/14). A source edit after Step 14 — a lint fix, a diff-review fix — needs a fresh Step 14 pass before the audit.
- **Auditor gap or `block-final`** → complete the step (a source edit re-opens Steps 13–14) → re-run the implementation-control gate (`resolve_work_package.py` + `Agent(implementation-auditor)`). **If a critical step is missing, do NOT finalize.**

## Red flags — STOP
- Coding before the spec/plan files exist · diverging from `docs/agentic-sdlc/specs`/`docs/agentic-sdlc/plans` without updating them · marking a gated step done while red · "works/passed/fixed" without real output · scope creep (a new finding is a **new task** in the plan file, not a bigger diff) · committing/pushing without explicit approval · inventing an API without Context7 · running independent work serially instead of delegating.

## Finalize
Only when: code done · TDD evidence file complete · relevant + full tests run with output shown · both `security-reviewer` passes done (or the Step 14 skip note) · lint/typecheck/build + secret-scan reported · diff reviewed · `implementation-auditor` verdict `allow-final`. Then invoke `completion-claim-gate` with the exact evidence you will claim, and only after that produce the **Final Implementation Report** (`templates.md`). No evidence → no "done"; report the honest current state instead.

## Artifact layout & per-package evidence
Work-package artifacts resolve in two layouts: the legacy flat `docs/agentic-sdlc/{specs,plans}/<id>.md` (back-compat, unchanged) and the per-package canonical `docs/agentic-sdlc/<slug>/{spec,plan,evidence}/<work_id>.md`, where `<slug>` is lowercase kebab-case `^[a-z0-9][a-z0-9-]{0,63}$` and never a reserved name (`specs`, `plans`, `evidence`, `notes`, `spec`, `plan`). Per-package plan change-detection runs as a filesystem scan, not a `git status` query; new generated plans can be git-ignored, so the resolver scans the filesystem; published plugin documentation is tracked separately.

From Step 8 the main loop writes the **TDD evidence file**: `docs/agentic-sdlc/<slug>/evidence/<work_id>.tdd.md` for a per-package work package, `docs/agentic-sdlc/evidence/<work_id>.tdd.md` for a flat one. The slug is the `<slug>` directory the spec and plan were saved in. Append every test run from Step 8 until the auditor is dispatched, including retests. Only a new pipeline run for the same work_id starts the file fresh. Run each test bare, then write each block with the file-edit tool, never a shell redirect, as its run happens (format and write rule → `playbook.md`). The file is complete before `Agent(implementation-auditor)` is dispatched, is git-ignored with no validator, never gates resolution, and masks secrets as `***MASKED***`.

On **Finalize**, persist the Final Implementation Report to `docs/agentic-sdlc/<slug>/evidence/<work_id>.md` — **per-package only** (flat packages get no Finalize evidence), using the slug emitted by `resolve_work_package.py` (never re-derived). A re-run **overwrites** this single canonical file in place (last run wins; no per-run/timestamp suffix). Evidence is git-ignored and has **no validator** — it never gates resolution. This write is performed by the **main pipeline finalize step**, not the read-only `implementation-auditor` sub-agent, which receives the resolver output, the diff and the TDD evidence path in its dispatch prompt and writes nothing.
