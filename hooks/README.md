# Hooks - Deterministic Guards + Conceptual Checklists

Two kinds of guard live here:

1. **Real hooks** - executable `.mjs` scripts wired by a runtime hook config.
2. **Conceptual hooks** - judgment-based checkpoints enforced by skills and contracts, not scripts.

> **Command-guard matcher is `Bash\|PowerShell`, with no `if` filter.** Both details are security-load-bearing.
> On a Windows host without Git Bash, Claude Code does not register the Bash tool at all, so a `Bash`-only
> matcher leaves every command guard inert. And an `if` narrowed to a git SUBCOMMAND (`Bash(git commit*)`)
> never starts the hook for a git alias such as `git ci`, so the guard cannot decide at all — the docs call
> `if` best-effort and say to use the permission system, not a hook filter, for a hard allow/deny. The
> decision therefore lives inside each guard, which self-gates cheaply on `git`.

The hook scripts are shared in this directory, but being present as a script is not the same as being wired by every runtime.

Claude Code paths resolve through `${CLAUDE_PLUGIN_ROOT}`. Codex exports `PLUGIN_ROOT` (0.171.0 also exports `CLAUDE_PLUGIN_ROOT`, but still replaces `${...}` tokens as raw text before shell parsing, so the loader below stays); its fixed Node launch code reads `process.env.PLUGIN_ROOT` and imports the handler through `pathToFileURL()`, keeping installed paths out of shell code. `commandWindows` selects `node.exe` on Windows; the default selects `node` on POSIX/WSL. Hook cwd remains the session project, independent of the installed package. Node must be on the hook PATH and hooks require native review/trust; see the [marketplace launch contract](../docs/runtime-adapter.md#codex-marketplace-hook-launch-contract).

Grok CLI exports `GROK_PLUGIN_ROOT` to hooks (plus a Claude root alias). Its command strings read the root inside fixed Node code and import a file URL; `commandWindows` is not a Grok field. ZCode passes `${ZCODE_PLUGIN_ROOT}` in shell-free `args[]` using `type: process` and `timeoutMs`. Kimi declares inline hooks, running relative handler paths with plugin-root cwd; the git checks take the Bash tool's `tool_input.cwd` (resolved against the session cwd) and fall back to stdin `cwd`. Grok command stdin uses `toolInput.command`, while Kimi/ZCode use `tool_input.command`. All require Node on the runtime hook PATH; no maintainer checkout is required. Output channels are runtime-adaptive through `hooks/hook-output.mjs`: the ZCode wire passes a literal `--zcode-runtime` argv element (and ZCode injects `ZCODE_PLUGIN_ROOT` as an environment variable), under which the scripts emit only ZCode-documented keys — a decision as `hookSpecificOutput` alone, a warn as `hookSpecificOutput.additionalContext` — because the advisory top-level `systemMessage` channel is a Claude Code convention outside ZCode's documented set (the live 2026-10-08 hook doc reports unknown fields ignored; the bundled `diagnosing-hooks` skill reports them as a failed run with the effect discarded). Every other runtime receives the payload unchanged.

### Claude Code wiring notes (`hooks-claude.json`)

`hooks-claude.json` carries no inline comments. It used to hold three `$comment` keys: two at
matcher-group level and one inside the `Stop` worktree-scan handler. Claude Code 2.1.330 logged a WARN
and an ERROR line on every plugin load for the two matcher-group keys
(`hooks.json: unknown keys "$comment" in hooks.PreToolUse[0], "$comment" in hooks.PreToolUse[1] ignored`; observed 2026-11-21 with
`claude -p --plugin-dir <package> --debug-file <log>` in an isolated `CLAUDE_CONFIG_DIR`). The log did
not name the handler-level key, and `claude plugin validate --strict` reported none of them. The current
[plugins reference](https://code.claude.com/docs/en/plugins-reference) (read 2026-11-21) documents no
comment field inside a matcher group or handler, so all three were removed, the rationale lives here, and
`tests/test_hooks_policy.py` fails if a `$comment` key comes back at any depth:

- **`PreToolUse` `Bash|PowerShell`** (scan-commit, destructive-command guard, branch guard): a
  Windows host without Git Bash registers no Bash tool, so a `Bash`-only matcher would leave the guards
  inert; and an `if` narrowed to a git subcommand never starts the hook for an alias such as `git ci`.
  Each guard self-gates on `git` instead (see the note under Runtime Wiring).
- **`PreToolUse` `Write|Edit|MultiEdit|Bash|PowerShell`** (flow-order guard): a source file written by
  a shell command (sed -i, a redirect, a heredoc, tee) is an edit like a Write/Edit, read by the shared
  write-target recognizer. No `if` filter, for the same reason as the command guards; the guard exits
  early when a command writes no source file.
- **`Stop` `worktree-scan.mjs`**: effect-layer detection. It scans the bytes that actually landed in
  the working tree, so the write form (tee/dd/base64/python -c/any redirect) does not matter; that is
  the class the command-string write guard documents as out of reach. Advisory by default;
  `AGENTIC_WORKTREE_SCAN_BLOCK=true` escalates it.
- The top-level `description` key stays: the 2.1.330 load log reported only the `$comment` keys.

It also reads what the same command stages before the commit: the unstaged diff of the paths that `add`/`stage`, the commit's own pathspecs, `-i`/`-o`, `--pathspec-from-file` or `-a` (inside a `bash -c` or `eval` payload too) put in the index, the contents of untracked files an `add` stages (5 MiB in total, binaries skipped, ignored files only under `-f`), and the patch file of a top-level `git apply`. `rm`, `mv` and `restore --staged` stage no working-tree content, so their paths are not read. The reads follow one order and one budget, because a hook killed by its 20-second timeout renders no decision: the staged diffs of the repositories the line commits in come first and their findings are reported at once; a staging directory that does not exist is skipped; a `-C` path holding an expansion falls back to the hook's own repository, with a notice. The budget is 48 git processes, 14 seconds, 32 MiB of scanned text and 5000 untracked files. A budget cut, a deadline or a signal that kills git during a commit repository's staged read (its diff or its `--name-only` list) DENIES the commit ("could not scan the staged changes"), right after the staged reads and before any later read; any other cut prints a loud "NOT scanned" notice, and so does a commit `-C` target that does not exist when the hook runs. When an alias stays unresolved (past the lookup cap, a different config context, the resolver's work budget, or an exception in the resolver), every directory a git call on the line runs in is scanned as if `commit -a` ran, and the hook says so. Flags credential files by name, including derived copies (`id_rsa.bak`, `.npmrc.old`, `server.key.bak`). Self-gates internally by resolving the git subcommand through `git-invocation.mjs`, so a git alias (`alias.ci = commit -a`) is still scanned. That resolver walks off the same shared `cmd_prefix` grammar as the destructive guard (`hooks/shell-prefix.mjs`) and reaches a git call inside an inner `-c`/`eval` payload, up to a depth of 3 and a bounded number of payloads per statement. **Past either bound the git path stops quietly** — unlike the destructive guard, which widens to a coarse linear scan rather than reporting clean. That asymmetry is deliberate for now: a coarse scan on the git path would have to guess which text is a commit message, and guessing wrong there blocks ordinary commits. It is a documented residual, not a covered case. A payload-derived call contributes its commit MESSAGE and its subcommand only: it does not gain a `-F`/`--file` read and its `-C` does not redirect the diff read, so reaching into a payload does not widen what this hook opens on disk. |

| `destructive-command-guard.mjs` | `PreToolUse` shell command | `PreToolUse` (`Bash`) | Blocks deterministic destructive commands such as `git reset --hard`, forceful `git clean`, recursive `rm` including wrapper/path forms, and `Remove-Item -Recurse` including common aliases/wrappers and the colon-bound switch form (`-Recurse:$true`; `-Recurse:$false` is the switch OFF and stays allowed), and cmd.exe's tree deletes (`rd`, `rmdir`, `del` or `erase` with `/s`, also run together as `/s/q`, glued to the name as `rd/s/q`, after `@` or `call`, or as Git Bash's `//s`) at the top level and inside a `cmd /c`, `/k` or `/r` payload (also `//c`, `cmd/c`, `/c` glued to the command, and cmd named as `%COMSPEC%` or `$env:ComSpec`), read without its `^` escapes and split on `&`, `&&` and `||`. `if exist <path> rd /s` and a command piped into cmd are not parsed. It also reads the command a second time with its comments blanked (bash `#`; PowerShell `#` and `<#…#>`) and its here-document bodies removed, so a quote inside a comment or a body cannot hide the next line, as `# don't forget` followed by a recursive delete did in base; this reading can only add findings. A `{…}` word that holds `"`, `$` or a backtick is not expanded as a brace word: the normal segmenter reads it, so a quoted `$(…)` inside it is still inspected. The payload walk is depth- and budget-bounded; past the bound it widens to a linear coarse scan rather than reporting clean. The prefix set is closed by the shell grammar; the wrapper table, shared with `git-invocation.mjs`, is an open-ended deny-list and is not claimed complete. |

Protected push resolution uses explicit destinations, local refs and relevant local push configuration, including source-only mappings and omitted-refspec defaults. Mirror and pruning of a destination range that can include `main`/`master` warn or deny even when those refs are absent locally: offline state cannot exclude remote deletion. Feature-only non-prune all/matching and feature-only/review-only ranges remain silent. The guard never connects to a remote. Its local Git queries are cached and bounded to one second/1 MiB each and four seconds total; errors or exhausted reads remain unknown. Expansion-derived forms, payload repository/config changes and command-supplied Git environment/include/path overrides do not gain new reads. A tag source with an unqualified destination has an unknown remote namespace and remains nonblocking unless another protected target is known; qualify the destination as `refs/heads/main` or `refs/tags/main` to remove that ambiguity.

Caller source-only remapping first requires a unique raw local-ref match. Ordinary `HEAD`/force-prefix operands without that match resolve later; a real ref named `+feature` keeps its matched canonical identity for mapping. Force is derived from the resulting request, while `--delete` keeps a literal plus-named target. Configured default refspecs use a separate path. Negative push refspecs filter concrete destination names after mapping/prune, with Git's case-sensitive matching. Prune checks all case variants covered by the existing protected-name policy, so a lowercase-only exclusion cannot rule out deletion of a differently cased remote protected ref. A qualified `^refs/heads/*` excludes the whole head namespace. Pattern checks invert over this fixed protected domain and a local ref set, rather than multiplying the number of refs by the number of refspecs.

Configured source queries have their own negative preflight: reverse configured destination patterns into source candidates, then test configured negatives before choosing the positive mapping. This differs from the final active destination exclusions. The latter are computed once for the fixed protected domain, so many positive/negative refspecs do not repeatedly rescan each other. Pattern substitution inserts captures as literal refname text, so replacement metacharacters such as `$&` cannot manufacture another wildcard.

Configured queries first check whether a positive mapping exists, deduplicate inverse candidates and index literal negatives. Remaining query work is bounded per push invocation to 8 Mi UTF-16 character units, charged from compared/generated string lengths. Exhaustion stays unresolved and nonblocking for that query, with no guessed same-name/upstream fallback; independently known explicit protected destinations are still checked. This bounds expensive local mapping resolution without claiming an unevaluated query safe.

Remote mirror booleans follow Git's word and signed32-bit base0 integer forms, including k/m/g units and hexadecimal/octal values. Invalid/overflow values remain unresolved; significant digits are bounded before numeric conversion.

## Effect Layer: What It Closes, And What It Does Not

The command guards read the raw command string and cannot be complete - shell aliases and
functions, `$PATH` shadowing, `eval` and variable indirection resolve after the hook has decided,
and the write surface is unbounded. The effect layer closes that class by never reading a command:
git runs `pre-commit`/`pre-merge-commit`/`commit-msg`/`prepare-commit-msg` on the OPERATION, and
`worktree-scan.mjs` reads bytes on disk.

The deterministic effect-layer tests (`tests/test_effect_layer_guards.py`) exercise a shell function wrapping `git commit`, an `eval`-assembled commit,
`git $C` indirection, a secret inside an alias-supplied message, `git commit --no-verify`, a
non-fast-forward merge commit, writes via `tee` / `base64 -d` / `python -c`, and a gitignored
`.env`. Their results establish handler behavior, not installed runtime delivery; retain fresh test output before citing a pass.

The optional Git message hooks scan the raw message file, including hash-prefixed lines. Git can retain those lines under nonedited/default, whitespace/verbatim or custom-comment-marker cleanup, so stripping them before scanning loses real message content. This conservative check may reject a secret in commentary that a later cleanup would remove; harmless templates and the existing same-line suppression/sample policy still apply. The one exception is the removed and context lines (and hunk headers) of git's own `git commit -v` diff below the scissors line: they are the file as it was, and git discards them, so a commit that removes a secret is no longer blocked. A line is skipped only when that diff really holds it; a typed line that merely looks like diff output is scanned. `prepare-commit-msg` checks the early message, while `commit-msg` also checks editor changes made afterward.

Stated limits, so nobody reads more into this than it delivers:

- `git -c core.hooksPath=/dev/null commit` disables all hooks - git documents this. A client-side
  hook is a fast local backstop; non-negotiable enforcement belongs server-side (`pre-receive`) or
  in CI.
- `Stop` does not fire on a user interrupt or an API error, so the working-tree scan can be skipped.
- The Stop scan is DETECTION: the bytes are already on disk when it runs. Prevention for the commit
  path is the git hook.
- A timed-out hook renders no decision at all, which is why the scan is bounded: it content-reads
  at most 200 untracked files and 4 MiB (ignored files get up to half when there are new files
  too, likely secret homes such as `.env` first), skips files over 256 KiB and vendor trees, and
  checks credential file names over every listed file. A secret beyond those bounds is not read.
- The command guards follow `git -C <dir>` and, on Kimi Code, the Bash tool's `cwd`. They do not
  follow `cd <dir> && git commit`, `--git-dir=`/`--work-tree=`, or `GIT_DIR=`/`GIT_WORK_TREE=`/
  `GIT_INDEX_FILE=` prefixes: such a commit is checked against the session directory. The installed
  git hook scans the operation itself, in the repository git runs it for.
- `scan-commit.mjs` models what the same command stages through `add`, `stage`, `rm`, `mv`,
  `restore --staged`, `apply` and the commit's own options. It does not model `checkout <rev> -- path`,
  `stash pop`, `cherry-pick -n`, `update-index`, a file another statement of the line creates, or a
  `-F -` message piped from `echo`, `printf`, `cat -`, `/bin/cat` or a `cat` with a redirect (a literal
  here-document piped from `cat <<WORD` is read); a `$` or backtick pathspec widens the read to the
  whole tree. The wrapper table both command resolvers share is a deny-list: `chroot`, `flock` and `watch`
  are not in it, glob command names and `{a..b}` sequences are not expanded, and PowerShell's
  `& { }` and `Invoke-Command` are not read. Base `f430715`'s false positives return by design: `echo hi #; git push …`, and a data heredoc
  that is not one of the exact shapes (an unquoted delimiter, `<<-`, extra redirects, other commands
  after it) is read as commands and may be denied. A heredoc that fills a hooks folder that is not a
  dot folder (`cat > hooks/pre-commit`, then a commit with `core.hooksPath=hooks`) is not detected when
  its body looks harmless. A single-quoted PowerShell here-string (`@'` ... `'@`) is read with its body
  blanked, so an apostrophe in it no longer hides the next line; a double-quoted one (`@"` ... `"@`)
  holding a `"` is not modelled. A git call past a resolver budget (payload statements, payload depth, alias walk) is
  not checked; `scan-commit.mjs` and `branch-guard.mjs` say so in their message instead of staying
  silent.
- On Windows, the Codex `commandWindows` launchers (and Grok's `node -e` commands) start `node.exe`
  through the runtime's hook shell in the project directory. If that shell is `cmd.exe` and
  `NoDefaultCurrentDirectoryInExePath` is unset, a `node.exe` planted in the project would run
  once the hooks are trusted. Which shell Codex uses is not verified offline, so the launchers are
  unchanged; set `NoDefaultCurrentDirectoryInExePath=1` in the user environment to close it.
- A repository `filter.<name>.clean` driver still runs when the scanners compare worktree files
  (`git diff HEAD`, `git status`), and a filter that rewrites a line can hide it from the Stop
  scan. No git setting disables arbitrary filter names; the staged scans read the index, which
  already holds the cleaned bytes git will commit.

### Codex

`worktree-scan.mjs` is not wired on Codex (VERIFY). Its default `systemMessage` output and optional Stop `decision: "block"` use documented Codex envelopes, and in its blocking mode the handler already checks `stop_hook_active`. ## Artifact Layouts And Per-Package Evidence

Work-package artifacts resolve in two layouts: the legacy flat `docs/agentic-sdlc/{specs,plans}/<id>.md` (back-compat, unchanged) and the per-package canonical `docs/agentic-sdlc/<slug>/{spec,plan,evidence}/<work_id>.md`, where `<slug>` is lowercase kebab-case `^[a-z0-9][a-z0-9-]{0,63}$` and never a reserved name (`specs`, `plans`, `evidence`, `notes`, `spec`, `plan`).

Per-package evidence persists to `docs/agentic-sdlc/<slug>/evidence/<work_id>.md` — per-package only (flat packages get no Finalize evidence), overwritten in place per run (single canonical file, last run wins), git-ignored, and with no validator (it never gates resolution, and no flow guard activates on an evidence write). That evidence write is performed by the main pipeline finalize step, not the read-only `implementation-auditor` sub-agent.

From Step 8 the pipeline's main loop also writes a TDD evidence file, `docs/agentic-sdlc/<slug>/evidence/<work_id>.tdd.md` per-package or `docs/agentic-sdlc/evidence/<work_id>.tdd.md` flat, with every test run until `implementation-auditor` is dispatched; it is git-ignored, has no validator and never gates resolution.

Per-package plan change-detection runs as a filesystem scan, not a `git status` query: new generated plans can be git-ignored, so the resolver scans the filesystem; published plugin documentation is tracked separately.

## Adding Or Disabling Hooks

- Add new scripts under the matching event in `hooks/hooks-claude.json` for Claude Code or `hooks/hooks-codex.json` for Codex when that runtime supports the event. The Grok adapter wire is `hooks/hooks-grok.json` and the Cursor adapter wire is `hooks/hooks-cursor.json`; do not copy Claude/Codex parsers into them, and do not create `hooks/hooks.json`.
- Use runtime hook controls to browse or temporarily disable hooks.
- Keep scripts deterministic. Checks that need judgment belong in skills/contracts.
