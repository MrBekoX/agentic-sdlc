# Release evidence — 0.6.0

Status: release preparation for version 0.6.0. The publish verdict is **do-not-publish**. This ledger was written on 2026-10-16 while the 0.6.0 changes were still uncommitted on the feature branch `feat/pipeline-zero-skill-delegation`, on top of public main `4262a19`. No release commit, tag, GitHub release, marketplace submission or portal upload existed when it was written.

## Scope and what changed since 0.5.0

The supported release runtimes stay Claude Code and Codex. Kimi Code, Grok CLI, ZCode, Cursor and Google Antigravity ship as experimental adapters; they are not 0.6.0 release targets and carry no go/no-go verdict. The 0.6.0 changes are listed under 0.6.0 in the [changelog](../CHANGELOG.md). The main one is breaking: `agentic-sdlc-pipeline` no longer invokes or reads the six focused skills. It reads the selected work type's core file at Steps 8–13 and dispatches the `security-reviewer` and `implementation-auditor` agents directly. The hook flow, the procedure-eval grader, the artifact status list and both SessionStart bootstraps change with it.

No model run recorded in this ledger was made on the 0.6.0 changes, and no new release-grade live run is in scope for 0.6.0. Following the maintainer's 2026-10-12 rule, every row whose requirement has a real earlier run records that run as a carried state instead of repeating it. Each row below holds one of four kinds of evidence:

- **Measured for 0.6.0 on 2026-10-16**: the version and changelog checks on the 0.6.0 working tree, and two read-only checks of the public repository (the release identity check and the private vulnerability reporting setting). None of them makes a model call.
- **Carried from an earlier run**: the state is that run's real result, PASS or FAIL, or GAP when the run covers the requirement only in a weaker form (an isolated diagnostic, earlier probes, a fixture capture, or a scan or install of an earlier package). It reads `carried from <commit or dated run>` and `not re-run on 0.6.0`, and the evidence cell names what changed since. A carried PASS is evidence about the package it measured, not a 0.6.0 measurement. `tests/test_release_ledger_docs.py` rejects a carried state that omits its source or scope, contradicts its source result in the 0.4.3 ledger or the compatibility matrix, or names a commit other than its Git commit cell, and a publish verdict rejects any required row carried without byte-identical inputs.
- **BLOCKED**: no run exists for 0.6.0 and none can be carried. Either the run needs a maintainer decision or an approved model run, or the row is defined on the 0.6.0 release commit, which did not exist yet. The local gate and the release secret scan are in this group; Phase 7 of the delivery plan makes the release commit and measures them on it.
- **GAP**: a run exists, but only in a form that cannot stand for the 0.6.0 requirement.

## Identity definitions

- **BR20 runtime payload identity**: the SHA-256 of the sha256sum-manifest form of the release archive members, one `<member sha256>  <path>` line per member sorted by UTF-8 path, excluding `docs/release-evidence-0.6.0.md` and `docs/release-readiness.md` (`scripts/build_release.py` `payload_identity` with `RUNTIME_PAYLOAD_EXCLUDE`, which follows `VERSION`). Identities carried from the [0.5.0 ledger](release-evidence-0.5.0.md) excluded `docs/release-evidence-0.5.0.md` instead, and those from the [0.4.3 ledger](release-evidence-0.4.3.md) excluded `docs/release-evidence-0.4.3.md`, so neither is comparable with a 0.6.0 identity. No 0.6.0 identity is recorded yet.
- **Skills-only payload identity**: the same manifest form over every member of the BR24 skills-only archive, with no exclusion.
- **Archive hash**: the SHA-256 of the archive file bytes.
- **Commit ids**: commit ids carried from the 0.4.3 and 0.5.0 ledgers belong to the original history, which the private archive repository keeps; the [history map](publication/history-map.md) gives the id of each one in this repository. `4262a19` and `8c81ed5786c7` are ids of the public history and need no mapping.
- **Routing input digest**: the SHA-256 of the prompt that `scripts/run_routing_eval.py` `build_codex_prompt` builds with an empty user prompt from `load_skills(skills/)`, followed by a newline and the scenario set `tests/skills/routing/using-agentic-sdlc.json` read as text (`codex_routing_input_digest` in `tests/test_release_ledger_docs.py`). It covers everything the Codex description classifier reads except its argv.

## Limits retained in the release decision

- Every model result in this ledger is carried from an earlier run, and none measured 0.6.0. Both routing passes measured the earlier skill descriptions; both pipeline procedures failed when they last ran, and no repair has been measured.
- The local gate and the release secret scan are BLOCKED until the release commit exists. The archive, manifest-validation and skills-only rows carry the 0.5.0 results.
- Codex test runs are wrapped in `/bin/bash -lc '…'` (on Windows, `powershell -Command "…"`), and the strict grader attributes neither form. Strict RED/GREEN therefore cannot pass on a real Codex transcript; for Codex, 0.6.0 acceptance is limited to the forbidden-skill, marker and reviewer-output checks. The gap is inherited from `require_red_green`.
- The validator's plan AC-coverage check fails open for `AC-1`-style or id-less acceptance criteria. It is left for a separate change and is not fixed in 0.6.0.
- No hook detects a slash-command-only pipeline activation; the offline procedure eval covers that case.
- The dispatch-terminal Stop check warns by default, blocks only under `AGENTIC_FLOW_GATE_BLOCK=true`, and runs only on Claude Code.
- The validator accepts the `approved` status but cannot prove who approved; only the pipeline's Approval receipt rule and the offline gate-stop case enforce it.
- Default (non-strict) procedure-eval mode still counts a Skill call whose arguments mention a required skill; strict mode closes that loophole.
- Real-profile Codex hook trust was not touched for 0.6.0; the trust rows carry the `26b0fe1983b3` measurements.
- Guard coverage is bounded, some checks are advisory or opt-in, and missing or unrecognized transcript evidence can fail open. See the [runtime adapter limits](runtime-adapter.md#limits-of-branch-review-result-and-strict-evidence).
