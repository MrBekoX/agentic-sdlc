# Release evidence — 0.7.0

Status: release preparation for version 0.7.0. The publish verdict is **do-not-publish**. This ledger was written on 2026-11-16 on the branch `chore/release-0.7.0`, on top of public main `7df82ed` (the pull request #25 merge). No release commit, tag, GitHub release, marketplace submission or portal upload existed when it was written. The static gate, archive, version and history-scan rows were measured on 2026-11-16 on the branch commit `ff49ebe03f73` (measured commit), before the branch was merged. A later commit that changes only this ledger keeps the measured runtime payload identity, while its own archive hash differs.

## Scope and what changed since 0.6.0

The supported release runtimes stay Claude Code and Codex. Kimi Code, Grok CLI, ZCode, Cursor and Google Antigravity ship as experimental adapters; they are not 0.7.0 release targets and carry no go/no-go verdict. The 0.7.0 changes are listed under 0.7.0 in the [changelog](../CHANGELOG.md). The main one is additive: the middleware-chain flow runner (`scripts/sdlc.py`, `scripts/sdlc_runner/` and `flows/`), the engines that run its joint spec/plan loop on Claude Code, Grok Build and ZCode, the runner-loop role cards for the other runtimes, the `draft-scribe` agent and one step file per runner card under `skills/<skill>/steps/`. The 16 skills keep their 0.6.0 procedures; none of them calls the runner yet. 0.7.0 also widens three hook guards (cmd.exe tree deletes, the Cursor shell guard, environment and URL secrets) and gives each CI gate job 120 minutes and main a CI concurrency group per commit.

Three changes that the changelog lists under 0.6.0 landed after the 0.6.0 measured commit `df7d0426a9a9` and are first measured here: the validator's plan AC-coverage fix (pull request #11, `55d5d60`), the 0.6.0 live-run fix round (`5b21df4`, in pull request #14) and the slash-command change's merge itself (pull request #10).

No model run recorded in this ledger was made on the 0.7.0 changes, and no new release-grade live run is in scope for 0.7.0. Following the maintainer's 2026-10-12 rule, every row whose requirement has a real earlier run records that run as a carried state instead of repeating it. Each row below holds one of four kinds of evidence:

- **Measured for 0.7.0 on 2026-11-16**: on this branch, the local gate, the release and skills-only archive builds, verifies and reproducibility, the version checks and the history scan of the branch; and read-only checks of the public repository (the release identity check, the private vulnerability reporting setting, and an anonymous mirror clone for personal data). None of them makes a model call.
- **Carried from an earlier run**: the state is that run's real result, PASS or FAIL, or GAP when the run covers the requirement only in a weaker form (an isolated diagnostic, earlier probes, a fixture capture, or a scan or install of an earlier package). It reads `carried from <commit or dated run>` and `not re-run on 0.7.0`, and the evidence cell names what changed since. A carried PASS is evidence about the package it measured, not a 0.7.0 measurement. `tests/test_release_ledger_docs.py` rejects a carried state that omits its source or scope, contradicts its source result in the 0.4.3 ledger or the compatibility matrix, or names a commit other than its Git commit cell, and a publish verdict rejects any required row carried without byte-identical inputs.
- **BLOCKED**: no run exists for 0.7.0 and none can be carried, because the run needs a maintainer decision or review, an approved model run or an upload, or has not been recorded yet.
- **GAP**: a run exists, but only in a form that cannot stand for the 0.7.0 requirement.

## Identity definitions

- **BR20 runtime payload identity**: the SHA-256 of the sha256sum-manifest form of the release archive members, one `<member sha256>  <path>` line per member sorted by UTF-8 path, excluding `docs/release-evidence-0.7.0.md` and `docs/release-readiness.md` (`scripts/build_release.py` `payload_identity` with `RUNTIME_PAYLOAD_EXCLUDE`, which follows `VERSION`). Identities carried from the [0.6.0 ledger](release-evidence-0.6.0.md), the [0.5.0 ledger](release-evidence-0.5.0.md) and the [0.4.3 ledger](release-evidence-0.4.3.md) excluded their own ledger instead, so none is comparable with a 0.7.0 identity.
- **Skills-only payload identity**: the same manifest form over every member of the BR24 skills-only archive, with no exclusion.
- **Archive hash**: the SHA-256 of the archive file bytes.
- **Commit ids**: commit ids carried from the 0.4.3 and 0.5.0 ledgers belong to the original history, which the private archive repository keeps; the [history map](publication/history-map.md) gives the id of each one in this repository. The ids the 0.6.0 ledger cites from before the 2026-10-17 public-history rewrite map as that ledger lists them.
- **Routing input digest**: the SHA-256 of the prompt that `scripts/run_routing_eval.py` `build_codex_prompt` builds with an empty user prompt from `load_skills(skills/)`, followed by a newline and the scenario set `tests/skills/routing/using-agentic-sdlc.json` read as text (`codex_routing_input_digest` in `tests/test_release_ledger_docs.py`). It covers everything the Codex description classifier reads except its argv.

## Limits retained in the release decision

- Every model result in this ledger is carried from an earlier run, and none measured 0.7.0. Both routing passes measured the descriptions before 0.6.0; both pipeline procedures failed when they last ran in the approved configuration, and the later 0.6.0 run outside it also failed.
- The flow runner, its three loop engines and the runner-loop role cards have no live run on any runtime. Their evidence is the deterministic suite (the engine parity tests drive each engine against a scripted model), and no skill invokes the runner in 0.7.0.
- The local gate, the archive rows and the secret scan are measured on the branch commit `ff49ebe03f73` before it is merged, not on the merge commit; they are repeated if the merged commit changes anything outside this ledger and `docs/release-readiness.md`, and the history scan and the personal-data sweep are repeated on the history that is actually pushed.
- Personal data published before 2026-10-17 is still reachable through GitHub's pull request refs #2–#9 until GitHub Support dereferences them (row `history_private_path_finding`).
- Codex test runs are wrapped in `/bin/bash -lc '…'` (on Windows, `powershell -Command "…"`), and the strict grader attributes neither form. Strict RED/GREEN therefore cannot pass on a real Codex transcript.
- Claude Code flow hooks read a slash-command start from the user record captured in headless `claude -p` on Claude Code 2.1.302; an interactive-session start was not captured, and no live pipeline run has exercised the slash path.
- The dispatch-terminal Stop check warns by default, blocks only under `AGENTIC_FLOW_GATE_BLOCK=true`, and runs only on Claude Code.
- The validator accepts the `approved` status but cannot prove who approved; only the pipeline's Approval receipt rule and the offline gate-stop case enforce it.
- Default (non-strict) procedure-eval mode still counts a Skill call whose arguments mention a required skill; strict mode closes that loophole.
- The destructive-command guard does not parse `if exist <path> rd /s` or a command piped into `cmd`, and the secret scanners do not report throwaway CI passwords such as `POSTGRES_PASSWORD: postgres`.
- Real-profile Codex hook trust was not touched for 0.7.0; the trust rows carry the `26b0fe1983b3` measurements.
- Guard coverage is bounded, some checks are advisory or opt-in, and missing or unrecognized transcript evidence can fail open. See the [runtime adapter limits](runtime-adapter.md#limits-of-branch-review-result-and-strict-evidence).
