# Runtime Adapter

AGENTIC-SDLC packages adapters for **Claude Code**, **Codex**, **Kimi Code**, **ZCode** and **Grok CLI**. Claude/Codex retain the full guard adapters and historical release evidence; the other three have narrower documented runtime coverage. This file defines the portable vocabulary and each adapter's actual boundaries. Packaging/replay support is separate from native lifecycle or public-directory acceptance; native install, discovery, update and uninstall results per runtime and OS are in the [compatibility matrix](publication/compatibility-matrix.md).

## Hook wiring and runtime boundaries

| Purpose | Claude Code | Codex |
|---|---|---|
| Commit secrets, destructive commands, branch policy | `scan-commit.mjs`, `destructive-command-guard.mjs`, `branch-guard.mjs`; `Bash` / `PowerShell` | Same handlers; `Bash` also matches native shell/unified-exec commands |
| Write secret scan | `scan-write.mjs`: PostToolUse advisory for `Write` / `Edit` / `MultiEdit` / `NotebookEdit`; VERIFY before using this Claude field-shape handler on Codex | `scan-write-codex.mjs`: PreToolUse denial for recognized literal `Bash` / `apply_patch` writes |
| Source-edit ordering | `flow-order-guard.mjs` on `Write` / `Edit` / `MultiEdit` and on `Bash` / `PowerShell`, where a shell write of a source file counts as an edit (the shared recognizer the Codex guard uses): warns by default; VERIFY before using this Claude field-shape handler on Codex | `flow-order-guard-codex.mjs`: default silent, opt-in denial; artifact or before-edit test evidence |
| Completion claim | `completion-claim-guard.mjs`: looks for an exact-name, non-errored `Skill` call to `completion-claim-gate`; VERIFY before using this Claude transcript reader on Codex | `completion-claim-guard-codex.mjs`: looks for the sentinel in the final assistant message through `codex-rollout.mjs` |
| Active-flow completion | `flow-step-guard.mjs`: Claude Skill/tool evidence; VERIFY before using this Claude transcript reader on Codex | `flow-step-guard-codex.mjs` and `codex-flow-evidence.mjs`: session-scoped artifact/command evidence |
| Working-tree secret detection | `worktree-scan.mjs`: Stop scan of changed/untracked bytes | Not wired; VERIFY this handler's installed-runtime behavior before porting |

The Claude command guards match both shells without a subcommand-level `if` filter; each handler resolves Git aliases and self-gates. Codex receives shell/patch content in `tool_input.command`, not Claude's `file_path` / `new_string` fields. Paths use the runtime root above; executable commands follow that runtime's shell contract.

### Codex marketplace hook launch contract

The marketplace installs a copy of the plugin; neither the source checkout nor a maintainer's home path is a runtime dependency. Codex exports `PLUGIN_ROOT` for the installed copy, while hook cwd is the user's session project. The [official hook reference](https://learn.chatgpt.com/docs/hooks) documents these variables, session cwd and the Windows-only `commandWindows` override (checked 2026-10-08).

All eight handlers use fixed `node -e` code that reads `process.env.PLUGIN_ROOT`, joins the named `hooks/<handler>.mjs`, sets `process.argv[1]` to preserve executable-entrypoint checks, and imports its `pathToFileURL()` URL. The installed path stays data throughout: spaces, Unicode, `$`, backticks, `&`, `#`, `%` and quotes valid on the host do not enter shell code or corrupt an ESM URL. `commandWindows` uses the same code with `node.exe`; POSIX and native WSL use `node`. This selects an executable name, not a shell or a WSL path conversion.

This avoids Codex's raw `${PLUGIN_ROOT}` replacement before shell parsing, confirmed in [0.161.0 discovery source](https://github.com/openai/codex/blob/979011409de0a60b52f179721948e65531d26144/codex-rs/hooks/src/engine/discovery.rs#L569). Every command hook runs through the selected shell; Windows may use cmd, PowerShell or a configured shell ([command runner](https://github.com/openai/codex/blob/979011409de0a60b52f179721948e65531d26144/codex-rs/hooks/src/engine/command_runner.rs#L384)). Do not interpolate an installed path into a hook command or pin a drive, username, checkout, cache directory, or Node installation path.

Re-checked against codex-cli 0.171.0 on 2026-11-21: Codex now also exports `CLAUDE_PLUGIN_ROOT` and `CLAUDE_PLUGIN_DATA` next to `PLUGIN_ROOT` and `PLUGIN_DATA` "for OOTB compat" ([discovery.rs L315-L320](https://github.com/openai/codex/blob/rust-v0.171.0/codex-rs/hooks/src/engine/discovery.rs#L315-L320)). It still replaces each `${KEY}` in the command string as raw text before the shell parses it ([L723-L725](https://github.com/openai/codex/blob/rust-v0.171.0/codex-rs/hooks/src/engine/discovery.rs#L723-L725)), and picks `commandWindows` on Windows when one is set ([L669-L671](https://github.com/openai/codex/blob/rust-v0.171.0/codex-rs/hooks/src/engine/discovery.rs#L669-L671)). Switching the token to `${CLAUDE_PLUGIN_ROOT}` would therefore gain nothing: a path with spaces or shell metacharacters still breaks shell parsing. The `node -e` environment loader and the separate `hooks/hooks-codex.json` stay. The value seen inside a running hook was not checked, because that needs hook trust.

Node.js must be available on the hook process PATH (`node.exe` on native Windows, `node` on POSIX/WSL). Installation does not install Node or grant hook trust. Review the current hook definitions in `/hooks`; changing either command field requires re-review. The universal public-directory `--skills-only` projection still excludes lifecycle hooks; this launch contract applies to hook-bearing repo/local marketplace packages.

`tests/test_codex_hook_portability.py` executes serialized commands from a relocated package and unrelated cwd, checks startup context and destructive/flow-order denials, and checks the handler/import/requirements/validator closure. `tests/skills/harness.py` also checks the fixed environment-loader references, including `commandWindows`. Windows cmd, Windows PowerShell and PowerShell 7, plus WSL `/bin/sh`, were checked on 2026-10-08: the five-test suite returned exit 0 with no skips on both hosts. A new reviewed Codex lifecycle run was not performed. These shell replays do not establish native discovery, trust or skill-trigger behavior.

The Codex flow-order switch `AGENTIC_FLOW_ORDER_BLOCK` and flow-step switch `AGENTIC_FLOW_GATE_BLOCK` are independent: the first enables pre-edit denial; the second escalates the Stop advisory. On Claude, `AGENTIC_FLOW_GATE_BLOCK` controls both flow guards. `AGENTIC_COMPLETION_GATE_BLOCK` controls completion-claim blocking on both runtimes. `AGENTIC_BRANCH_GUARD_BLOCK` and `AGENTIC_WORKTREE_SCAN_BLOCK` control their separate guards. A wired guard can still be advisory, disabled by default, or skipped while trust is pending.

## ZCode adapter (experimental — not a 0.4.3 release target)

ZCode (Z.ai) is an adapter target, not a supported release target; the supported release targets remain Claude Code and Codex. The schema below was fetched on 2026-09-19 from the official ZCode docs (`zcode.z.ai/en/docs/plugin`, `zcode.z.ai/en/docs/skill`, `zcode.z.ai/en/docs/hooks`) plus the `zai-org/zcode-plugins` CONTRIBUTING/distribution docs; nothing in this section is written from memory. ZCode reads `.zcode-plugin/plugin.json` first (falling back to `.claude-plugin/plugin.json`), adds this repository's root `marketplace.json` (ZCode schema) as a file source (`zcode.z.ai/en/docs/plugin`, fetched 2026-11-21, describes a repository catalog as a root `marketplace.json`: "list them in a marketplace.json at the root", so a directory or GitHub source is expected to use the same root `marketplace.json`, not natively observed; `.claude-plugin` appears there only in the plugin-manifest lookup, so a `.claude-plugin/marketplace.json` catalog fallback is undocumented), discovers skills from a flat `skills/<name>/SKILL.md` layout, and auto-loads `hooks/hooks.json` — which is why this repo ships a separate `hooks/hooks-zcode.json` and never creates `hooks/hooks.json`.

Adapter files: `.zcode-plugin/plugin.json`, the root `marketplace.json` (ZCode schema; the Claude marketplace file is untouched), `hooks/hooks-zcode.json`, and `.zcode-plugin/README.md` (+ `README_CN.md`), locked by `tests/test_zcode_packaging.py`.

Portable capability mapping: skills, commands, and agents are shared unchanged; the plugin root variables are `ZCODE_PLUGIN_ROOT` (with a `CLAUDE_PLUGIN_ROOT` alias injected for compatibility, per the fetched hook doc). The command guards reuse `scan-commit.mjs` / `destructive-command-guard.mjs` / `branch-guard.mjs` on `Bash`; the write scan reuses `scan-write.mjs` on `Write|Edit` (ZCode's `tool_input` carries `file_path` + `content` for Write, and Edit carries `new_string`); `session-start.mjs` runs on `startup|resume|clear|compact`. Executors are `type: process` argv with `timeoutMs` — no shell layer. Matchers are limited to tool names observed in a live ZCode session; `MultiEdit` and a PowerShell tool are not wired.

Documented gaps: the Stop completion/flow guards (they read Claude transcripts or Codex rollouts) and `worktree-scan.mjs` (no ZCode Stop adapter exists yet), the `flow-order-guard.mjs` (Claude field-shape assumptions unverified on ZCode), and `PermissionRequest` / `PostToolUseFailure` / `UserPromptSubmit` (no house handlers). The deny decision and SessionStart context use fields the fetched hook reference documents (`hookSpecificOutput.permissionDecision`, `hookSpecificOutput.additionalContext`); the advisory `systemMessage` user channel is not part of that documented protocol. Output channels are runtime-adaptive (`hooks/hook-output.mjs`): the wire passes a literal `--zcode-runtime` argv element and ZCode injects `ZCODE_PLUGIN_ROOT` as an environment variable (live hook doc, 2026-10-08), so under ZCode the scripts emit only documented keys — warns, including the shared write scanner's advisory, reach the model as `hookSpecificOutput.additionalContext`, and the advisory top-level `systemMessage` channel (a Claude Code convention the live doc reports as ignored and the bundled `diagnosing-hooks` skill reports as a failed run with the effect discarded, pitfall 8) is never written; other runtimes receive the payload unchanged. Locked by `tests/test_zcode_hook_output.py`. Native delivery/display remains unverified. ZCode added dynamic workflows in client 3.14.0 (official changelog, 2026-09-19: "a single script to orchestrate multiple sub-agents", started from the input-box plus menu or the `/workflow` command). The docs site has no workflow page (`zcode.z.ai/en/docs/workflow` and `/workflows` both 404), while the open-source client (zai-org/ZCode v3.14.3, `saved-workflows/store.ts`) stores saved workflows in `.zcode/workflows/` and `~/.zcode/workflows/` — and `plugin.json` has no `workflows` component key, so **a plugin install cannot deliver one**. Since 0.7.0 `workflows/zcode/spec-plan-draft.dwf.ts` is the flow runner's driver: on an explicit workflow request the runner prints a `CreateWorkflow` launch for it, and it hands each role card to a new actor. It has not run on a live ZCode client, and no skill calls the runner yet; until such a run exists the deferred-adapter fallback rule below applies (author -> critic -> revise with saved artifacts and `validate_artifacts.py` evidence). Documented installs add the root `marketplace.json` as a file source; a directory or GitHub-repository source (`MrBekoX/agentic-sdlc`, for an install without a clone) is expected to use the same root `marketplace.json` (docs fetched 2026-11-21; not natively observed); whether ZCode falls back to `.claude-plugin/marketplace.json` is undocumented and not observed (see [`.zcode-plugin/README.md`](../.zcode-plugin/README.md)). The official zai-org/zcode-plugins catalog has a reviewed submission process; no submission has been performed here. See the [publication checklist](publication/zcode-marketplace.md) for layout, bilingual README, validator and native-evidence requirements. Packaging/replay evidence does not certify native lifecycle behavior; native lifecycle evidence is recorded separately in the [compatibility matrix](publication/compatibility-matrix.md): on Windows, Linux and macOS (E9, E15, E14) the ZCode desktop 3.14.5 bundle's agent CLI 0.16.9 validated, installed (16 skills, 5 hook declarations), updated and uninstalled the plugin in isolated profiles. That evidence does not cover the desktop GUI flow, hook execution or live model behavior.

## Grok CLI adapter (experimental — not a 0.4.3 release target)

Grok CLI is an adapter target, not a supported release target; the supported release targets remain Claude Code and Codex. The schema below was read on 2026-09-19 from the local user-guide (`~/.grok/docs/user-guide/09-plugins.md`, `08-skills.md`, `10-hooks.md`, `16-subagents.md`) plus live `grok plugin --help` / `validate --help` / `install --help` on grok 1.0.34; nothing in this section is written from memory. Grok reads `.grok-plugin/marketplace.json` as the marketplace index and accepts `.grok-plugin/plugin.json` (also the `.claude-plugin/` equivalents). Standard plugin discovery is `skills/`, `commands/`, `agents/`, and `hooks/hooks.json` at the plugin root — which is why this repo ships a separate `hooks/hooks-grok.json` declared by the Grok manifest and never creates `hooks/hooks.json`.

Adapter files: `.grok-plugin/plugin.json`, `.grok-plugin/marketplace.json`, `hooks/hooks-grok.json`, and `.grok-plugin/README.md`, locked by `tests/test_grok_packaging.py`. The Grok-facing `description` is not the Claude-only sentence (`Claude Code skill library…`). `grok plugin validate .` going green against the Claude layout is compatibility discovery, not Grok-native publish.

Portable capability mapping: skills, commands and agents share the library. Grok exports `GROK_PLUGIN_ROOT` to hook processes with a `CLAUDE_PLUGIN_ROOT` alias. Three `type: command` guards use fixed `node -e` code reading `process.env.GROK_PLUGIN_ROOT`, joining the handler and importing its `pathToFileURL()` URL. Root bytes never enter shell source. Timeouts are in seconds; Grok does not support Codex `commandWindows` or ZCode argv fields. Hook stdin is camelCase (`toolName`, `toolInput.command`); replay tests deliberately omit the Claude snake_case fallback. Node must be on the selected shell PATH and use the same OS/path environment as Grok. Hook failures remain fail-open, so a handler replay is distinct from native hook delivery/trust. See [current official hook runner](https://github.com/xai-org/grok-build/blob/main/crates/codegen/xai-grok-hooks/src/runner/command.rs) and [multi-platform distribution](publication/multi-platform-distribution.md), checked 2026-10-10.

Documented gaps: write-scan stays unwired until a captured `search_replace` hook stdin shows which `toolInput` keys carry the new text (`file_path` / `new_string` are Claude; assuming them on Grok is a silent miss). Stop completion/flow guards and `worktree-scan.mjs` stay unwired: the completion and flow guards read Claude transcripts or Codex rollouts, and all three test the snake_case `stop_hook_active`, while the Grok hook guide (`10-hooks.md`, checked 2026-11-21) gives `Stop` a camelCase payload with `stopHookActive` and `lastAssistantMessage` and says a script reading `.stop_hook_active` must switch to `.stopHookActive`; no live Grok Stop payload has been captured. `session-start.mjs` assumes a Claude payload and delivers its context on stdout, but for `SessionStart` stdout is ignored (same guide), so it is not wired. Both stay unwired until a Grok output mode exists. Grok workflows are Rhai, discovered from the project catalog `.grok/workflows/*.rhai` (and user `~/.grok/workflows/*.rhai`), not as a plugin component — `grok plugin details` still inventories skills/commands/agents/hooks only. This clone ships Rhai ports of the three Claude JS loops at `.grok/workflows/spec-plan-draft.rhai`, `multi-lens-review.rhai`, and `skill-draft.rhai`. Claude `workflows/*.js` stay the Claude runtime source and are not loaded by Grok. `grok plugin install` to another machine does not deliver those project-catalog scripts. The flow runner's engine `workflows/grok/spec-plan-draft.rhai` does ship in the package: the runner copies it into the work package and launches it by `script_path`, so it needs no catalog entry. Two `spec-plan-draft.rhai` files therefore exist, as different programs with different consumers: `.grok/workflows/spec-plan-draft.rhai` is the 0.6.0 project-catalog script that `/workflow spec-plan-draft` reaches in a clone, not delivered by `grok plugin install`; `workflows/grok/spec-plan-draft.rhai` is the 0.7.0 runner engine, which `scripts/sdlc_runner/loop.py` stages byte for byte and records with its sha256. Merging them would break the engine pins in `tests/test_grok_rhai_workflows.py` and the byte-for-byte ship check; the catalog script is to be removed in a follow-up once the skills that name `/workflow spec-plan-draft` move onto the runner. When the named script is in the catalog and workflows are enabled, a Grok session invokes `/workflow <name>` or the `workflow` tool; otherwise the fallback is `spawn_subagent` plus author -> critic -> revise with saved artifacts and `validate_artifacts.py` evidence. Documented distribution includes trusted local-directory installs, personal catalogs and pinned remote sources. Use `grok plugin install <package-directory> --trust`, which also enables the plugin (`grok plugin enable` is needed only after a `grok plugin disable`); marketplace-name installs require a resolvable catalog entry. The official [xai-org/plugin-marketplace](https://github.com/xai-org/plugin-marketplace) accepts reviewed PRs with source SHA/index/validation requirements: every `url` source must pin a full 40-character `sha` (its README, checked 2026-11-21), which the shipped `.grok-plugin/marketplace.json` `url` source does not carry; that only matters for the official marketplace or under `[marketplace] require_sha = true` / `GROK_MARKETPLACE_REQUIRE_SHA=1` (`09-plugins.md`). No submission has been performed here. Native install, discovery, update and uninstall of a local package passed in isolated profiles on Windows, Linux and macOS with Grok 1.0.50 ([compatibility matrix](publication/compatibility-matrix.md) E3, E8, E13); hook delivery and live model behavior remain unverified; see [publication steps](publication/grok-marketplace.md). Plugin-agent frontmatter must not declare `mcpServers`, hooks, or `permissionMode: bypassPermissions` (`16-subagents.md`).

Grok's command guards match `Bash|run_terminal_command`; they consume the native
`toolName` and `toolInput.command` fields. The other runtimes retain their own wires.

## Kimi Code adapter (experimental runtime coverage; packaged distribution)

Kimi declares `.kimi-plugin/plugin.json`, `skills`, `commands`, `agents`,
`sessionStart.skill` and `skillInstructions`; `marketplace-kimi.json` uses schema
version `2`, distinct from the plugin version. Three inline PreToolUse Bash hooks
run `node "./hooks/<handler>.mjs"` with plugin-root cwd. Stdin `tool_input.command`
selects the command. The guards take the target project from the Bash tool's own
`tool_input.cwd`, where Kimi runs the command (resolved against the session cwd),
and fall back to the stdin `cwd`. `KIMI_PLUGIN_ROOT` is documented for hooks,
not as a global Bash alias. The mapping resolves helper paths from the loaded
Skill file. Discovered custom Agent profiles may be used; otherwise pass the role
instructions to an available built-in profile. Shared `WebFetch` allowlists do not
automatically grant Kimi `FetchURL`.

No Claude/Codex transcript reader, write scanner or Stop guard is wired on Kimi.
SessionStart uses the named router skill (`sessionStart.skill`), not an invented hook
output field. Stop and SessionStart stay unwired because Kimi's contract differs
(hooks reference, checked 2026-11-21): a Stop hook blocks with exit 2 and a stderr
reason or with stdout `hookSpecificOutput.permissionDecision: "deny"`, SessionStart
is observation-only with exit-0 stdout "may be appended to context", and the payload
has no transcript field and no `stop_hook_active`. The shared Stop handlers print
Claude-style `decision`/`systemMessage` JSON and exit 0, and `session-start.mjs`
prints `additionalContext` JSON. A future Kimi mode would need exit-2 Stop results,
plain-text SessionStart output, loop protection without `stop_hook_active`, no
transcript dependency and the project from the payload `cwd`. Unverified without a
live Kimi run: whether hooks of a GitHub-installed plugin run, and whether Kimi
accepts the extra `hookEventName` key in the wired guards' deny payload (exit 2 with
a stderr reason is the unambiguous fallback). Details are in
[`.kimi-plugin/README.md`](../.kimi-plugin/README.md#why-stop-and-sessionstart-stay-unwired).
The native installer, reinstall-based update and removal passed in isolated profiles

## Cursor adapter

Cursor is an adapter target. The supported release targets remain Claude Code and Codex. The manifest and component rules below were fetched on 2026-10-14 from [cursor.com/docs/plugins](https://cursor.com/docs/plugins) and [cursor.com/docs/reference/plugins](https://cursor.com/docs/reference/plugins). Hook events and payload fields were fetched the same day from [cursor.com/docs/hooks](https://cursor.com/docs/hooks). Plugin hook working directories and `CURSOR_PLUGIN_ROOT` / `CURSOR_PROJECT_DIR` were taken from Cursor staff's 2026-04-13 forum reply on plugin hook cwd, not from the hooks reference (that page documents project, user, team and enterprise hook cwd, and does not describe plugin-hook cwd).

Cursor discovers a plugin from `.cursor-plugin/plugin.json`. This repository is one plugin at the root, so component paths point at the shared `skills/`, `commands/` and `rules/` directories, and the `agents` path at `cursor/agents/`, Cursor's copies of the shared role files. `hooks/hooks.json` is not created: ZCode and Grok auto-load that filename, and Claude Code loads it in addition to its declared wire. The Cursor manifest points at `hooks/hooks-cursor.json`.

Each command is fixed `node -e` code. It reads `process.env.CURSOR_PLUGIN_ROOT`, joins `hooks/cursor-launch.mjs`, and imports that file URL. The installed path stays in the environment. `hooks/cursor-launch.mjs` then loads a sibling handler from its own file URL and translates Cursor's payload:

| Cursor event | Shared handler | Cursor result |
|---|---|---|
| `beforeShellExecution` | `scan-commit.mjs`, `destructive-command-guard.mjs`, `branch-guard.mjs` | `permission: deny` for a deny, `ask` for a warning, `allow` otherwise. Shell text is presented as `tool_input.command` with `tool_name: Bash`, which makes the shared guard apply both POSIX and PowerShell readings. A guard that crashes or answers with anything but a JSON object denies the command; empty output is an allow. When the project folder is gone, the guard runs from the launcher's own folder. |
| `preToolUse` (`Write`, `Edit`, `StrReplace`, `ApplyPatch`; flow-order also `Delete`) | `scan-write.mjs`, `flow-order-guard.mjs` | A write-scan finding becomes `permission: deny`, because `afterFileEdit` documents no model-visible output. The scan reads only the new text: before the write the file on disk is the old one, so it is never scanned, and a `Delete` is not write-scanned. Flow-order denies only when `AGENTIC_FLOW_GATE_BLOCK` is set; its default warning has no Cursor channel and is not turned into a deny. |
| `sessionStart` | `session-start.mjs` | `additional_context`, plus a Cursor invocation note. The child cwd is the project (`CURSOR_PROJECT_DIR`, else the hook `cwd`). |
| `stop` | `worktree-scan.mjs` | `followup_message` only when `AGENTIC_WORKTREE_SCAN_BLOCK` is set and the scan reports a finding. The default advisory is not forwarded: Cursor's documented stop output is `followup_message`, and using it for a warning would start another turn. |

`completion-claim-guard.mjs` and `flow-step-guard.mjs` stay unwired. They read Claude transcript records. Cursor's `stop` input documents `status` and `loop_count`, plus the common `transcript_path`, and that file is not a Claude transcript.

There is no Claude `Workflow` tool. Spec and plan use the embedded author → critic → revise adapter and the role files in `cursor/agents/`. Skills are invoked as `/<skill-name>` or by reading the installed `SKILL.md`. The manual command id is `git-safety-check`.

Install with `python3 scripts/install_cursor_plugin.py install` from the package directory. The destination is `Path.home() / ".cursor" / "plugins" / "local" / "agentic-sdlc"` unless `--dest` is set. Cursor's own documentation says a symlink in `~/.cursor/plugins/local` loads only when its target is inside that folder, so the installer copies. Install refuses a destination that holds files but no install receipt (`error=cursor_dest_not_empty`), and an update refuses when a path the new package adds already holds a file the installer did not write (`error=cursor_dest_file_unmanaged:<path>`). The receipt is written before the first copy, so an interrupted install can be retried or uninstalled. A managed path or a receipt that is a symlink is refused, and on Linux and macOS uninstall deletes through folder handles opened without following links. From a git checkout the installer copies only `git ls-files` minus the release exclusion classes, never `.env`, `settings.local.json`, `AGENTS.md`, `CLAUDE.md`, `CLAUDE.local.md`, session reports or audit dumps; a checkout git cannot list is refused (`error=cursor_package_unreadable`) rather than copied from the working tree. An extracted package is walked under the same exclusions. Update copies again and deletes only files listed in the previous install receipt. Uninstall deletes those receipt files and leaves every other file, including Cursor settings outside the destination. Node.js (`node` on `PATH`), Python 3.8+ and Git are checked first.

A team marketplace import uses `.cursor-plugin/marketplace.json` (`source: "."`, marketplace name `mrbekox`). Public marketplace submission is prepared in [cursor-marketplace.md](publication/cursor-marketplace.md) and has not been sent. ## Codex flow evidence and limits

`flow-order-guard-codex.mjs` allows a recognized source edit after either a same-work-id spec/plan pair written in this rollout and validated strictly, or a recorded invocation of a recognized test runner. A RED run counts for ordering: the pre-edit check deliberately does not require a successful test result. The current call is never prior evidence: its own `&& pytest` runs after the edit, so it is dropped by its call id, or without an id as an identical command with no recorded output. On-disk-only artifacts do not satisfy the pair; a single patch that bundles artifacts and source is not prior evidence. An unreadable rollout or unavailable validator fails open; a readable rollout with missing/unresolvable required artifacts can deny.

`flow-step-guard-codex.mjs` activates only when this rollout records a spec/plan write. It attaches spec/plan/test obligations only when a non-test source edit is also observed. Artifact checks use strict validation and same-work-id pairing. Test evidence requires a recognized runner invocation; `echo pytest` does not qualify. A correlated exit code 0 satisfies the result check; a nonzero exit does not. A missing exit code fails open to invocation-only evidence. Correlation uses `call_id`, first taking the recorded `function_call_output` exit line and then the structured `exec_command_end` fallback.

A correlated exit code counts only when it is attributable to the runner (BR6, default-on). The command is split into statements on unquoted `;`, newline and `||`. A command that holds `;`, newline or `||` and lies outside the safe shell grammar described under the limits below is not attributable. Otherwise real-runner attribution requires the runner to be the last statement: `pytest; echo EXIT=$?` and `pytest || true` lose attribution, and so does a trailing version-only or help-only runner such as `pytest; pytest --version` or `pytest; npm test -- --help`. In a trailing `||` run every operand must be a real runner, and every operand before the last must have no unquoted pipe and no background `&`. `&&` chains keep attribution (`cd repo && pytest`, `pytest && pytest --version`), because `&&` is not a BR6 split. Pipelines such as `pytest | tee log.txt` keep default attribution as a documented limit. A background job (an unquoted, unescaped `&` not joined to another operator) in the last statement keeps default attribution and is not attributable under strict evaluation (DP33). A standalone `pytest --version` stays default-accepted, and a run with no correlated exit code keeps the fail-open, invocation-only outcome.

Native Codex 0.154.0 WSL records successful patches as `custom_tool_call` / `custom_tool_call_output`, and shell exits as `Process exited with code N`. The reader retains historical carriers and accepts these current ones. It reads only leading native metadata before `Output:` or unknown text; tool-output or denial-echo headers are not exit evidence. A current custom patch needs its own correlated exit 0 and a success marker at the start of the actual output body. Missing, refused, failed, mismatched-type, or conflicting-call records do not count as successful patch writes. The captured fixture and mutations in `tests/test_codex_current_rollout.py` pin this boundary.

These checks do not establish test quality or freshness after the latest source edit: they scan the whole rollout, do not bind a test to one work id, and do not require a test-summary signature. A successful `pytest --version` can qualify. The parser also cannot guarantee that a runner-shaped segment in a compound shell command actually executed. Run and inspect the real final verification separately. The current allowlist includes `make test`, `npm test` / `npm run test`, yarn/pnpm test forms, `node --test`, `bun test`, `dotnet test`, `gradlew test`, `tox`, and `nox`, alongside direct Python/JS/Go/Rust/JVM runners. A runner also counts behind `time`, `timeout N`, `env`, `nice`, a path (`.venv/bin/pytest`, `./gradlew`), a launcher (`uv`/`poetry`/`pipenv run`, `npx`, `bunx`, `pnpm exec`), Python interpreter flags, or a shell wrapper (`bash`/`sh -c`, `powershell`/`pwsh -Command`, `cmd /c`), checked to a depth of 3; a heredoc body and a `#` comment are never a run. Other wrappers and arbitrary shell scripts remain outside the invocation recognizer. This shape check is separate from BR6 exit attribution below; strict BR6 attribution does not count `node --test` or `gradlew` as runners.

Flow evidence recognizes `apply_patch` targets (an `*** Move to:` target and a Bash `apply_patch <<'PATCH'` body included), ordinary `>` / `>>` targets (quoted, or at the start of the command as `>src/app.py`), and operands of `sed -i` and `tee`, including multi-file writes. The current-edit recognizer respects quotes, heredocs (`<<'EOF'`, `<<"EOF"`, `<<\EOF` and CRLF, one grammar shared with the secret-write extractor), expansion-dependent targets, and the actual tool name. The Claude flow guards use the same recognizer for `Bash` and `PowerShell` commands. A CR belongs to a heredoc delimiter only when it directly follows the delimiter word on the opener line, as bash reads it. A Bash `apply_patch` heredoc counts only for the exact command word `apply_patch` or `applypatch` (any path prefix), before `<<` or after `|` on the opener line. Paths are classified relative to the project after `.` and `..` segments are resolved. A path that names the project through a link (macOS `/var` is `/private/var`) is retried with its folder and the project folder resolved, also when the hook falls back to its own working directory; the retry can only make a path a source file, and its work is bounded. The Codex pre-edit guard and both Stop guards read every target as written before they resolve any link. The flow hooks analyse at most 128 KiB of each recorded shell command: a longer one is not read, so it is never test-run or write evidence. On Claude it counts as a possible source edit, so inside an active flow Stop keeps every obligation, even when the command wrote nothing. The current command of the flow-order guard is read up to the recognizer's 512 KiB cap. The prior-write reader is broader and can over-approximate writes. Unrecognized copy/encoding commands without a recognized redirect, expansion-derived targets, source deletes, PowerShell cmdlet writes (`Set-Content`, `Out-File`), and extended/fd redirects (`&>`, `&>>`, `>|`, `N>`, `>&N`) remain bounded gaps. Recognizing a target for flow evidence does not mean its content is covered by the secret scanner: that scanner scans only literal added content from patch/printf/echo/heredoc forms. Arbitrary tee/base64/command-substitution output is not checkable by this layer and remains fail-open.

Other limits remain material:

- The rollout reader has an 8 MiB ceiling; literal write extraction has a 512 KiB bound. Missing, unreadable, or oversized inputs can suppress enforcement.
- Artifact-less refactors and implementation resumed with only prior-session artifacts do not activate the Codex flow-step backstop. `Skill` / `Workflow` / `Agent`-only security, control, and dispatch steps are not observed by this adapter. The pipeline's security and control steps are `Agent`-only (`security-reviewer`, `implementation-auditor`), so on Codex they are covered by the offline strict grader, not by a hook.
- Completion-claim patterns are narrow: English claims with their inflections and a few Turkish phrases. Questions and quoted or fenced spans are not claims, while a `>` Markdown line is read. A claim is hypothetical only through its own clause (a conditional or an opening once/until in it, a modal up to three words before the claim, a Turkish future form) or an earlier clause of its sentence that opens with a conditional and reaches the claim through commas only (a `;` or `:` starts an independent clause), and a negation counts only inside the claim's sentence. The sentinel must appear in the final assistant message; prior quoted/user messages do not count. A model can still repeat the marker without good evidence, so its presence is not proof of correctness.
- Stop adapters check `stop_hook_active` to avoid repeated continuation. They use payload `cwd`, falling back to the hook process directory; unresolved artifact locations can prevent useful evidence. Missing/unreadable inputs fail open, but malformed JSONL lines are skipped: a still-readable partial rollout can lack evidence and trigger a flow-order denial.

### Limits of branch, review-result and strict evidence

The publication decision blocks in the [current release ledger](release-evidence-0.7.0.md), the [0.6.0 ledger](release-evidence-0.6.0.md), the [0.5.0 ledger](release-evidence-0.5.0.md) and the [0.4.3 ledger](release-evidence-0.4.3.md) link this section.

- The live Codex Stop hook does not report the `branch` step. The Codex branch report is the `strict_branch=protected|ok|unknown` line of the offline `scripts/strict_flow_evidence.py --rollout <path> --cwd <dir>`.
- Codex rollouts expose no reviewer dispatch event, so `review-result` is Claude-only.
- On Claude, `branch` observes the working-directory branch at Stop time. An edit made on `main` followed by a checkout of another branch is missed; `branch-guard.mjs` still covers commits and pushes. Both `branch` and `review-result` are warn-level steps and never block, under any flag.
- `AGENTIC_FLOW_STRICT_EVIDENCE` (`true`, `1` or `yes`, case-insensitive; default off) makes the live Codex `tests` evidence strict. Claude test evidence is judged strictly only by the procedure eval's `--strict-evidence`; the flag does not change the live Claude outcome.
- These properties are not observable by the hooks: the work-type core read before the first edit, whether the pipeline's `red-first` test run failed, the full pipeline step order, an approved (as opposed to schema-valid) spec or plan, reviewer independence, and re-review after a hook-definition change. The offline strict grader checks the core read (`core-read`), the failing run before the first production edit and the `required_order` sequence; the validator accepts `status: approved` but cannot prove who approved.
- Hook enforcement of the `agentic-sdlc-pipeline` steps beyond spec, plan and tests covers Claude Code only; the Codex flow-step Stop backstop checks only the merged spec, plan and tests steps. The `dispatch` step needs a `Skill` call to `dispatch-strategy`, and its `security` and `control` steps need `Agent` dispatches of `security-reviewer` and `implementation-auditor`, each matched by exact name (the name or `agentic-sdlc:<name>`). Its `red-first` step needs a test command before a production-source edit; it has no Stop key, so it never joins the Codex Stop gate. The Step 11 and 14 security lenses must therefore be direct `Agent(security-reviewer)` calls, in parallel in one message when they fan out, never a `Workflow` or an agent-team, which the exact-name match does not count. On Claude Code, `flow-step-guard.mjs` also warns when a pipeline turn ends on the `dispatch-strategy` decision, and blocks that only under `AGENTIC_FLOW_GATE_BLOCK=true`. Codex is covered by the offline strict grader (`scripts/run_procedure_eval.py --strict-evidence`).
- Claude Code flow hooks read a slash-command start from the top-level user record that opens, after optional whitespace, with `<command-message>` or `<command-name>` and names `<command-name>/<skill></command-name>`. That shape was captured in headless `claude -p` on Claude Code 2.1.302; an interactive-session start was not captured, and a version that records the start differently activates no flow. A prompt the user opens with those tags also activates the flow. Slash starts on the other adapters are not known to activate a flow (Cursor runs the same reader on its own transcript format; Kimi, Grok and ZCode wire no flow guard). No live pipeline run has exercised the slash path yet.
- Codex wraps test runs in `/bin/bash -lc '…'`, and on Windows in `powershell -Command "…"`. The grader attributes neither wrapper as a test run, so the strict red/green checks (`require_red_green`, `red_before_source_edit`) cannot pass on real Codex transcripts. Codex acceptance is limited to the forbidden-skill, marker and reviewer-output checks.
- Windows hook support is worded as the current [Codex hooks page](https://learn.chatgpt.com/docs/hooks) states it, as captured 2026-09-14: a Windows-only `commandWindows` command override and a `windows_managed_dir` setting.
- The post-install check `scripts/check_codex_hook_trust.py` reports hook trust state from `hooks/list` only; it does not prove that a hook runs, that `node` is on PATH, or that a trusted hook has an effect.
- Exit attribution is lexical. An exit code is attributed only while the command stays inside a safe shell grammar: unquoted words, single quotes, double quotes without command substitution, plain `$NAME` parameters, word-start comments, backslash escapes, the separators `;`, newline, `||`, `&&`, `|` and `&`, simple redirections such as `> out.txt` or `2>&1`, and command words that are external programs or the builtins `cd`, `echo`, `export`, `pwd`, `true`, `false`, `:` and `set -euo pipefail`. Any other syntax or command word, for example `$(`, a backtick, `${`, `(`, `{`, `[[`, `<<`, `printf`, `test`, `[`, `unset`, `wait`, `eval`, `source`, `alias`, `hash`, `trap`, `exec`, `set -n`, an assignment to an integer-attributed variable such as `RANDOM` or `OPTIND`, or an `export` argument that is not a literal `NAME=value` or plain word, makes a command that also holds `;`, newline or `||` unattributable by default and makes every command unattributable under strict evaluation, so a legitimate `cd repo; pytest $(cat args)` or `source .venv/bin/activate; pytest` reports `tests` missing. Not detected by the live Codex hook, `AGENTIC_FLOW_STRICT_EVIDENCE`, `scripts/strict_flow_evidence.py` or the procedure eval's `--strict-evidence`: how the runner name resolves or behaves outside the command text, such as `PATH=b:$PATH; pytest` after writing `b/pytest`, a `package.json` test script or a function inherited from the shell profile; and, by default only, a command without `;`, newline or `||` such as `set -n && pytest`, which never runs pytest. (D23, DP35)
- Test-runner arguments are read the way bash reads them. An argument is compared after quote and backslash removal, and an unquoted `<`, `>` or `&>` ends a word, so `pytest --version>out.txt` is version-only. Only a `&&` segment that itself runs the test runner counts, so `echo pytest && pytest --version` reports `tests` missing. An argument with a `$` expansion, or one without `/` that holds a glob character or starts with `~`, counts as a possible version or help flag, so `cd repo; pytest $ARGS` and `pytest; pytest -k test_*` report `tests` missing. Only space, tab and newline separate words; every other character, including U+00A0, is part of a word. A Superpowers delivery read counts only when it is the single `cat` statement of its command and reads one literal canonical absolute path under `<CODEX_HOME or ~/.codex>/plugins/cache/`; any other form is Ambiguous. The offline `scripts/strict_flow_evidence.py` uses the `CODEX_HOME` of its own process, so a rollout captured elsewhere is graded with `CODEX_HOME` set to that capture's home. `git` and `node` are started only from an absolute path found in an absolute `PATH` entry, and never as batch files. (D25, DP37)

## Coexistence and session restoration

Select one process owner before focused routing: explicit user selection wins; otherwise preserve the current phase's owner across resume/compact; a new house entry defaults to AGENTIC-SDLC. Bootstrap, router, and focused design guidance carry the same rule. Namespacing identifies a skill but does not select a process owner. Security hooks remain independent of that choice.

Before substantive phase content, load the selected owner's actual instructions. After resume, compaction, or a supplied summary, reload the selected procedure and continue from saved progress without repeating completed approvals; reuse an already-loaded body only in uninterrupted context. `mind-spark/SKILL.md` contains only the entry/loading gate. Its complete house design procedure is in `references/design-process.md` and is loaded only for an AGENTIC-SDLC-owned design phase; foreign-owned entry loads that owner's skill instead. This boundary was introduced after a live direct-entry failure, and its current behavior is measured separately from lifecycle delivery.

The reference snapshot [Superpowers b36e0829c6d0140e93cfef2ca599b1b07d4a7797](https://github.com/obra/superpowers/tree/b36e0829c6d0140e93cfef2ca599b1b07d4a7797) has a Claude SessionStart matcher `startup|clear|compact`, omitting `resume`; the house Claude hook has no matcher restriction. ## Pipeline Spec/Plan Rule

`agentic-sdlc-pipeline` owns internal Spec and Plan phases. Claude Code uses `spec-plan-draft`; Codex uses the embedded author -> critic -> revise adapter. The pipeline must not call standalone `spec-authoring` or `plan-authoring` for its internal steps 4-5.

## Artifact Layouts And Per-Package Evidence

Work-package artifacts resolve in two layouts on both runtimes: the legacy flat `docs/agentic-sdlc/{specs,plans}/<id>.md` (back-compat, unchanged) and the per-package canonical `docs/agentic-sdlc/<slug>/{spec,plan,evidence}/<work_id>.md`, where `<slug>` is lowercase kebab-case `^[a-z0-9][a-z0-9-]{0,63}$` and never a reserved name (`specs`, `plans`, `evidence`, `notes`, `spec`, `plan`).

Current Codex switch semantics (since 0.4.3): `AGENTIC_FLOW_GATE_BLOCK` controls only the flow-step Stop
backstop; `AGENTIC_FLOW_ORDER_BLOCK` controls only `flow-order-guard-codex.mjs`. They are independent.
The flow-order guard resolves both flat and canonical per-package spec/plan layouts through the same
artifact lookup used by the Codex Stop evidence engine. Any older “shared-env coupling” wording in
historical design material is superseded by this runtime contract.

Per-package evidence persists to `docs/agentic-sdlc/<slug>/evidence/<work_id>.md` — per-package only (flat packages get no Finalize evidence), overwritten in place per run (single canonical file, last run wins), git-ignored, and with no validator (it never gates resolution; the flow guards on neither runtime activate on an evidence write). That evidence write is performed by the main pipeline finalize step, not the read-only `implementation-auditor` sub-agent.

From Step 8 the pipeline's main loop also writes a TDD evidence file, `docs/agentic-sdlc/<slug>/evidence/<work_id>.tdd.md` per-package or `docs/agentic-sdlc/evidence/<work_id>.tdd.md` flat, with every test run until `implementation-auditor` is dispatched; it is git-ignored, has no validator and never gates resolution.

Per-package plan change-detection runs as a filesystem scan, not a `git status` query: new generated plans can be git-ignored, so the resolver scans the filesystem; published plugin documentation is tracked separately.
