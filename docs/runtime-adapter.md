# Runtime Adapter

AGENTIC-SDLC packages adapters for **Claude Code**, **Codex**, **Kimi Code**, **ZCode** and **Grok CLI**. Claude/Codex retain the full guard adapters and historical release evidence; the other three have narrower documented runtime coverage. This file defines the portable vocabulary and each adapter's actual boundaries. Packaging/replay support is separate from native lifecycle or public-directory acceptance; native install, discovery, update and uninstall results per runtime and OS are in the [compatibility matrix](publication/compatibility-matrix.md).

## Hook wiring and runtime boundaries

| Purpose | Claude Code | Codex |
|---|---|---|
| Commit secrets, destructive commands, branch policy | `scan-commit.mjs`, `destructive-command-guard.mjs`, `branch-guard.mjs`; `Bash` / `PowerShell` | Same handlers; `Bash` also matches native shell/unified-exec commands |
| Write secret scan | `scan-write.mjs`: PostToolUse advisory for `Write` / `Edit` / `MultiEdit`; VERIFY before using this Claude field-shape handler on Codex | `scan-write-codex.mjs`: PreToolUse denial for recognized literal `Bash` / `apply_patch` writes |
| Source-edit ordering | `flow-order-guard.mjs`: warns by default; VERIFY before using this Claude field-shape handler on Codex | `flow-order-guard-codex.mjs`: default silent, opt-in denial; artifact or before-edit test evidence |
| Completion claim | `completion-claim-guard.mjs`: looks for a Skill invocation; VERIFY before using this Claude transcript reader on Codex | `completion-claim-guard-codex.mjs`: looks for the sentinel in the final assistant message through `codex-rollout.mjs` |
| Active-flow completion | `flow-step-guard.mjs`: Claude Skill/tool evidence; VERIFY before using this Claude transcript reader on Codex | `flow-step-guard-codex.mjs` and `codex-flow-evidence.mjs`: session-scoped artifact/command evidence |
| Working-tree secret detection | `worktree-scan.mjs`: Stop scan of changed/untracked bytes | Not wired; VERIFY this handler's installed-runtime behavior before porting |

The Claude command guards match both shells without a subcommand-level `if` filter; each handler resolves Git aliases and self-gates. Codex receives shell/patch content in `tool_input.command`, not Claude's `file_path` / `new_string` fields. Paths use the runtime root above; executable commands follow that runtime's shell contract.

### Codex marketplace hook launch contract

The marketplace installs a copy of the plugin; neither the source checkout nor a maintainer's home path is a runtime dependency. Codex exports `PLUGIN_ROOT` for the installed copy, while hook cwd is the user's session project. The [official hook reference](https://learn.chatgpt.com/docs/hooks) documents these variables, session cwd and the Windows-only `commandWindows` override (checked 2026-10-08).

All eight handlers use fixed `node -e` code that reads `process.env.PLUGIN_ROOT`, joins the named `hooks/<handler>.mjs`, sets `process.argv[1]` to preserve executable-entrypoint checks, and imports its `pathToFileURL()` URL. The installed path stays data throughout: spaces, Unicode, `$`, backticks, `&`, `#`, `%` and quotes valid on the host do not enter shell code or corrupt an ESM URL. `commandWindows` uses the same code with `node.exe`; POSIX and native WSL use `node`. This selects an executable name, not a shell or a WSL path conversion.

This avoids Codex's raw `${PLUGIN_ROOT}` replacement before shell parsing, confirmed in [0.161.0 discovery source](https://github.com/openai/codex/blob/979011409de0a60b52f179721948e65531d26144/codex-rs/hooks/src/engine/discovery.rs#L569). Every command hook runs through the selected shell; Windows may use cmd, PowerShell or a configured shell ([command runner](https://github.com/openai/codex/blob/979011409de0a60b52f179721948e65531d26144/codex-rs/hooks/src/engine/command_runner.rs#L384)). Do not interpolate an installed path into a hook command or pin a drive, username, checkout, cache directory, or Node installation path.

Node.js must be available on the hook process PATH (`node.exe` on native Windows, `node` on POSIX/WSL). Installation does not install Node or grant hook trust. Review the current hook definitions in `/hooks`; changing either command field requires re-review. The universal public-directory `--skills-only` projection still excludes lifecycle hooks; this launch contract applies to hook-bearing repo/local marketplace packages.

`tests/test_codex_hook_portability.py` executes serialized commands from a relocated package and unrelated cwd, checks startup context and destructive/flow-order denials, and checks the handler/import/requirements/validator closure. `tests/skills/harness.py` also checks the fixed environment-loader references, including `commandWindows`. Windows cmd, Windows PowerShell and PowerShell 7, plus WSL `/bin/sh`, were checked on 2026-10-08: the five-test suite returned exit 0 with no skips on both hosts. A new reviewed Codex lifecycle run was not performed. These shell replays do not establish native discovery, trust or skill-trigger behavior.

The Codex flow-order switch `AGENTIC_FLOW_ORDER_BLOCK` and flow-step switch `AGENTIC_FLOW_GATE_BLOCK` are independent: the first enables pre-edit denial; the second escalates the Stop advisory. On Claude, `AGENTIC_FLOW_GATE_BLOCK` controls both flow guards. `AGENTIC_COMPLETION_GATE_BLOCK` controls completion-claim blocking on both runtimes. `AGENTIC_BRANCH_GUARD_BLOCK` and `AGENTIC_WORKTREE_SCAN_BLOCK` control their separate guards. A wired guard can still be advisory, disabled by default, or skipped while trust is pending.

## ZCode adapter (experimental — not a 0.4.3 release target)

ZCode (Z.ai) is an adapter target, not a supported release target; the supported release targets remain Claude Code and Codex. The schema below was fetched on 2026-09-19 from the official ZCode docs (`zcode.z.ai/en/docs/plugin`, `zcode.z.ai/en/docs/skill`, `zcode.z.ai/en/docs/hooks`) plus the `zai-org/zcode-plugins` CONTRIBUTING/distribution docs; nothing in this section is written from memory. ZCode reads `.zcode-plugin/plugin.json` first (falling back to `.claude-plugin/plugin.json`), adds this repository's root `marketplace.json` (ZCode schema) as a file source (a directory or GitHub source is read through `.claude-plugin/marketplace.json` first), discovers skills from a flat `skills/<name>/SKILL.md` layout, and auto-loads `hooks/hooks.json` — which is why this repo ships a separate `hooks/hooks-zcode.json` and never creates `hooks/hooks.json`.

Adapter files: `.zcode-plugin/plugin.json`, the root `marketplace.json` (ZCode schema; the Claude marketplace file is untouched), `hooks/hooks-zcode.json`, and `.zcode-plugin/README.md` (+ `README_CN.md`), locked by `tests/test_zcode_packaging.py`.

Portable capability mapping: skills, commands, and agents are shared unchanged; the plugin root variables are `ZCODE_PLUGIN_ROOT` (with a `CLAUDE_PLUGIN_ROOT` alias injected for compatibility, per the fetched hook doc). The command guards reuse `scan-commit.mjs` / `destructive-command-guard.mjs` / `branch-guard.mjs` on `Bash`; the write scan reuses `scan-write.mjs` on `Write|Edit` (ZCode's `tool_input` carries `file_path` + `content` for Write, and Edit carries `new_string`); `session-start.mjs` runs on `startup|resume|clear|compact`. Executors are `type: process` argv with `timeoutMs` — no shell layer. Matchers are limited to tool names observed in a live ZCode session; `MultiEdit` and a PowerShell tool are not wired.

Documented gaps: the Stop completion/flow guards and `worktree-scan.mjs` (they read Claude transcripts or Codex rollouts; no ZCode Stop adapter exists yet), the `flow-order-guard.mjs` (Claude field-shape assumptions unverified on ZCode), and `PermissionRequest` / `PostToolUseFailure` / `UserPromptSubmit` (no house handlers). The deny decision and SessionStart context use fields the fetched hook reference documents (`hookSpecificOutput.permissionDecision`, `hookSpecificOutput.additionalContext`); the advisory `systemMessage` user channel is not part of that documented protocol. Output channels are runtime-adaptive (`hooks/hook-output.mjs`): the wire passes a literal `--zcode-runtime` argv element and ZCode injects `ZCODE_PLUGIN_ROOT` as an environment variable (live hook doc, 2026-10-08), so under ZCode the scripts emit only documented keys — warns, including the shared write scanner's advisory, reach the model as `hookSpecificOutput.additionalContext`, and the advisory top-level `systemMessage` channel (a Claude Code convention the live doc reports as ignored and the bundled `diagnosing-hooks` skill reports as a failed run with the effect discarded, pitfall 8) is never written; other runtimes receive the payload unchanged. Locked by `tests/test_zcode_hook_output.py`. Native delivery/display remains unverified. ZCode added dynamic workflows in client 3.14.0 (official changelog, 2026-09-19: "a single script to orchestrate multiple sub-agents", started from the input-box plus menu or the `/workflow` command). The docs site has no workflow page (`zcode.z.ai/en/docs/workflow` and `/workflows` both 404), while the open-source client (zai-org/ZCode v3.14.3, `saved-workflows/store.ts`) stores saved workflows in `.zcode/workflows/` and `~/.zcode/workflows/` — and `plugin.json` has no `workflows` component key, so **a plugin install cannot deliver one**. The port at `workflows/zcode/spec-plan-draft.dwf.ts` is therefore an UNVERIFIED shape, kept as a starting point for a live run, not a supported path; until such a run exists the deferred-adapter fallback rule below applies (author -> critic -> revise with saved artifacts and `validate_artifacts.py` evidence). Documented installs add the root `marketplace.json` as a file source; a directory or GitHub-repository source (`MrBekoX/agentic-sdlc`, for an install without a clone) is read through `.claude-plugin/marketplace.json` first and shows the Claude entry (see [`.zcode-plugin/README.md`](../.zcode-plugin/README.md)). The official zai-org/zcode-plugins catalog has a reviewed submission process; no submission has been performed here. See the [publication checklist](publication/zcode-marketplace.md) for layout, bilingual README, validator and native-evidence requirements. Packaging/replay evidence does not certify native lifecycle behavior; native lifecycle evidence is recorded separately in the [compatibility matrix](publication/compatibility-matrix.md): on Windows, Linux and macOS (E9, E15, E14) the ZCode desktop 3.14.5 bundle's agent CLI 0.16.9 validated, installed (16 skills, 5 hook declarations), updated and uninstalled the plugin in isolated profiles. That evidence does not cover the desktop GUI flow, hook execution or live model behavior.

## Grok CLI adapter (experimental — not a 0.4.3 release target)

Grok CLI is an adapter target, not a supported release target; the supported release targets remain Claude Code and Codex. The schema below was read on 2026-09-19 from the local user-guide (`~/.grok/docs/user-guide/09-plugins.md`, `08-skills.md`, `10-hooks.md`, `16-subagents.md`) plus live `grok plugin --help` / `validate --help` / `install --help` on grok 1.0.34; nothing in this section is written from memory. Grok reads `.grok-plugin/marketplace.json` as the marketplace index and accepts `.grok-plugin/plugin.json` (also the `.claude-plugin/` equivalents). Standard plugin discovery is `skills/`, `commands/`, `agents/`, and `hooks/hooks.json` at the plugin root — which is why this repo ships a separate `hooks/hooks-grok.json` declared by the Grok manifest and never creates `hooks/hooks.json`.

Adapter files: `.grok-plugin/plugin.json`, `.grok-plugin/marketplace.json`, `hooks/hooks-grok.json`, and `.grok-plugin/README.md`, locked by `tests/test_grok_packaging.py`. The Grok-facing `description` is not the Claude-only sentence (`Claude Code skill library…`). `grok plugin validate .` going green against the Claude layout is compatibility discovery, not Grok-native publish.

Portable capability mapping: skills, commands and agents share the library. Grok exports `GROK_PLUGIN_ROOT` to hook processes with a `CLAUDE_PLUGIN_ROOT` alias. Three `type: command` guards use fixed `node -e` code reading `process.env.GROK_PLUGIN_ROOT`, joining the handler and importing its `pathToFileURL()` URL. Root bytes never enter shell source. Timeouts are in seconds; Grok does not support Codex `commandWindows` or ZCode argv fields. Hook stdin is camelCase (`toolName`, `toolInput.command`); replay tests deliberately omit the Claude snake_case fallback. Node must be on the selected shell PATH and use the same OS/path environment as Grok. Hook failures remain fail-open, so a handler replay is distinct from native hook delivery/trust. See [current official hook runner](https://github.com/xai-org/grok-build/blob/main/crates/codegen/xai-grok-hooks/src/runner/command.rs) and [multi-platform distribution](publication/multi-platform-distribution.md), checked 2026-10-10.

Documented gaps: write-scan stays unwired until a captured `search_replace` hook stdin shows which `toolInput` keys carry the new text (`file_path` / `new_string` are Claude; assuming them on Grok is a silent miss). Stop completion/flow guards and `worktree-scan.mjs` stay unwired — they read Claude transcripts or Codex rollouts; Grok Stop fields (`lastAssistantMessage`, `stopHookActive`, `reason == "end_turn"`) were not captured this session. `session-start.mjs` assumes a Claude payload and is not wired. Grok workflows are Rhai, discovered from the project catalog `.grok/workflows/*.rhai` (and user `~/.grok/workflows/*.rhai`), not as a plugin component — `grok plugin details` still inventories skills/commands/agents/hooks only. This clone ships Rhai ports of the three Claude JS loops at `.grok/workflows/spec-plan-draft.rhai`, `multi-lens-review.rhai`, and `skill-draft.rhai`. Claude `workflows/*.js` stay the Claude runtime source and are not loaded by Grok. `grok plugin install` to another machine does not deliver those project-catalog scripts. When the named script is in the catalog and workflows are enabled, a Grok session invokes `/workflow <name>` or the `workflow` tool; otherwise the fallback is `spawn_subagent` plus author -> critic -> revise with saved artifacts and `validate_artifacts.py` evidence. Documented distribution includes trusted local-directory installs, personal catalogs and pinned remote sources. Use `grok plugin install <package-directory> --trust`, which also enables the plugin (`grok plugin enable` is needed only after a `grok plugin disable`); marketplace-name installs require a resolvable catalog entry. The official [xai-org/plugin-marketplace](https://github.com/xai-org/plugin-marketplace) accepts reviewed PRs with source SHA/index/validation requirements; no submission has been performed here. Native install, discovery, update and uninstall of a local package passed in isolated profiles on Windows, Linux and macOS with Grok 1.0.50 ([compatibility matrix](publication/compatibility-matrix.md) E3, E8, E13); hook delivery and live model behavior remain unverified; see [publication steps](publication/grok-marketplace.md). Plugin-agent frontmatter must not declare `mcpServers`, hooks, or `permissionMode: bypassPermissions` (`16-subagents.md`).

Grok's command guards match `Bash|run_terminal_command`; they consume the native
`toolName` and `toolInput.command` fields. The other runtimes retain their own wires.

## Cursor adapter

Cursor is an adapter target. The supported release targets remain Claude Code and Codex. The manifest and component rules below were fetched on 2026-10-14 from [cursor.com/docs/plugins](https://cursor.com/docs/plugins) and [cursor.com/docs/reference/plugins](https://cursor.com/docs/reference/plugins). Hook events and payload fields were fetched the same day from [cursor.com/docs/hooks](https://cursor.com/docs/hooks). Plugin hook working directories and `CURSOR_PLUGIN_ROOT` / `CURSOR_PROJECT_DIR` were taken from Cursor staff's 2026-04-13 forum reply on plugin hook cwd, not from the hooks reference (that page documents project, user, team and enterprise hook cwd, and does not describe plugin-hook cwd).

Cursor discovers a plugin from `.cursor-plugin/plugin.json`. This repository is one plugin at the root, so component paths point at the shared `skills/`, `agents/`, `commands/` and `rules/` directories. `hooks/hooks.json` is not created: ZCode and Grok auto-load that filename, and Claude Code loads it in addition to its declared wire. The Cursor manifest points at `hooks/hooks-cursor.json`.

Each command is fixed `node -e` code. It reads `process.env.CURSOR_PLUGIN_ROOT`, joins `hooks/cursor-launch.mjs`, and imports that file URL. The installed path stays in the environment. `hooks/cursor-launch.mjs` then loads a sibling handler from its own file URL and translates Cursor's payload:

| Cursor event | Shared handler | Cursor result |
|---|---|---|
| `beforeShellExecution` | `scan-commit.mjs`, `destructive-command-guard.mjs`, `branch-guard.mjs` | `permission: deny` for a deny, `ask` for a warning, `allow` otherwise. Shell text is presented as `tool_input.command` with `tool_name: Bash`, which makes the shared guard apply both POSIX and PowerShell readings. A crash fails closed. |
| `preToolUse` (`Write`, `Edit`, `StrReplace`, `ApplyPatch`, `Delete`) | `scan-write.mjs`, `flow-order-guard.mjs` | A write-scan finding becomes `permission: deny`, because `afterFileEdit` documents no model-visible output. Flow-order denies only when `AGENTIC_FLOW_GATE_BLOCK` is set; its default warning has no Cursor channel and is not turned into a deny. |
| `sessionStart` | `session-start.mjs` | `additional_context`, plus a Cursor invocation note. The child cwd is the project (`CURSOR_PROJECT_DIR`, else the hook `cwd`). |
| `stop` | `worktree-scan.mjs` | `followup_message` only when `AGENTIC_WORKTREE_SCAN_BLOCK` is set and the scan reports a finding. The default advisory is not forwarded: Cursor's documented stop output is `followup_message`, and using it for a warning would start another turn. |

`completion-claim-guard.mjs` and `flow-step-guard.mjs` stay unwired. They read Claude transcript records. Cursor's `stop` input documents `status` and `loop_count`, plus the common `transcript_path`, and that file is not a Claude transcript.

There is no Claude `Workflow` tool. Spec and plan use the embedded author → critic → revise adapter and the shared `agents/` roles. Skills are invoked as `/<skill-name>` or by reading the installed `SKILL.md`. The manual command id is `git-safety-check`.

Install with `python3 scripts/install_cursor_plugin.py install` from the package directory. The destination is `Path.home() / ".cursor" / "plugins" / "local" / "agentic-sdlc"` unless `--dest` is set. Cursor's own documentation says a symlink in `~/.cursor/plugins/local` loads only when its target is inside that folder, so the installer copies. Update copies again and deletes only files listed in the previous install receipt. Uninstall deletes those receipt files and leaves every other file, including Cursor settings outside the destination. Node.js (`node` on `PATH`), Python 3.8+ and Git are checked first.

A team marketplace import uses `.cursor-plugin/marketplace.json` (`source: "."`, marketplace name `mrbekox`). Public marketplace submission is prepared in [cursor-marketplace.md](publication/cursor-marketplace.md) and has not been sent. Native IDE install, Customize discovery and a live model turn were not run in the packaging environment: `cursor` and `cursor-agent` were not on `PATH`. Static manifest checks and relocated hook replays are not that IDE session.

## Google Antigravity adapter (experimental — not a supported release target)

Google Antigravity (AGY / Antigravity 2.0 IDE) is an experimental adapter target, not a supported release target; the supported release targets remain Claude Code and Codex. The schema and discovery rules below were verified on 2026-10-15 against the built-in Antigravity customization references (`agy-customizations`, `plugin`, `antigravity-guide`) and the live `https://antigravity.google/schemas/v1/plugin.json` JSON Schema (`additionalProperties: false`).

Antigravity discovers workspace plugins at `<workspace>/.agents/plugins/<plugin-name>/` and global user plugins at `~/.gemini/config/plugins/<plugin-name>/`. Unlike Claude Code or Codex, Antigravity requires `plugin.json` at the root of the installed plugin directory (`<plugin-dir>/plugin.json`) and enforces a strict two-key schema (`name` matching `^[a-zA-Z0-9-_]+$` and `description`), rejecting `version`, `skills`, `hooks`, `author`, `license`, and any other extra keys (`additionalProperties: false`). Because placing a `plugin.json` at the repository root would trigger Codex's broken portable `AgentPlugin` loader branch (see [Portable manifest discovery gap on 0.154.0](#portable-manifest-discovery-gap-on-01540)), the Antigravity manifest is stored at `.antigravity-plugin/plugin.json` and tracked in `scripts/bump_version.py` under `VERSIONLESS_PLUGIN_MANIFESTS` so `bump_version.py --check` enforces its strict two-key schema without injecting `"version"`.

Adapter files: `.antigravity-plugin/plugin.json` and `.antigravity-plugin/README.md`, locked by `tests/test_antigravity_packaging.py` and `tests/test_packaging_metadata.py`. See [`.antigravity-plugin/README.md`](../.antigravity-plugin/README.md) for staging commands that copy `.antigravity-plugin/plugin.json` to `<plugin-dir>/plugin.json` alongside the shared `skills/`, `contracts/`, `scripts/`, `assets/`, `commands/`, `workflows/`, `docs/`, and `agents/` directories.

Portable capability mapping and verified runtime boundaries:
- **Skills and `<runtime-root>` resolution**: Antigravity discovers `<plugin-dir>/skills/<skill-name>/SKILL.md` (requiring only `name` and `description` in YAML frontmatter). Antigravity does not substitute `${CLAUDE_PLUGIN_ROOT}` or `${PLUGIN_ROOT}` in skill text; skills resolve `<runtime-root>` via the portable **Plugin root** rule (two directory levels above the loaded `SKILL.md` file), which resolves to `<plugin-dir>` in both workspace and global installs.
- **Rules**: Antigravity natively auto-loads `AGENTS.md` from the workspace root (`always_on`).
- **Subagents (`agents/*.md`)**: Antigravity subagents are invoked via `invoke_subagent(Subagents=[{TypeName, Role, Prompt, ...}])` using built-in `research` (read-only) or `self` (full toolset) types, or defined in `<plugin-dir>/agents/<name>.yaml`. In the Antigravity customizations reference, a `.md` subagent frontmatter declaring an unrecognized tool name in `tools:` (such as Claude's `Read`, `Grep`, `Glob`, `Bash`) can fail tool validation (`subagent stalls at "Initializing..."`). When delegating a specialist review role on Antigravity, read `<runtime-root>/agents/<role-name>.md`, strip its YAML frontmatter, and pass the markdown role body in `Prompt` to `invoke_subagent` with `TypeName="research"` (read-only) or `TypeName="self"`. Do not copy `agents/*.md` into `.agents/agents/` without translating their frontmatter and tool lists.
- **Workflows**: Legacy Antigravity `.agent/workflows/*.md` files are slash-command prompt macros scheduled for deprecation on **October 19, 2026** (`migrate-workflows` converts them into `SKILL.md` files). They are not equivalent to Claude Code's JavaScript `Workflow` engine (`workflows/*.js`). Do not create `.agent/workflows/*.md` files; use the embedded author → critic → revise adapter (`invoke_subagent` or degraded single-session pass) plus deterministic `validate_artifacts.py` checks.
- **Hooks**: Antigravity only supports `PreToolUse` and `PostToolUse` in `hooks.json`, using `toolCall.name` / `toolCall.arguments` (with tool names such as `run_command`, `view_file`, `replace_file_content`, `write_to_file`) and top-level `{"decision": "allow"|"deny", "reason": "..."}` stdout JSON. It does not support `SessionStart` or `Stop` hooks, and does not inject `CLAUDE_PLUGIN_ROOT` or `PLUGIN_ROOT`. Consequently, no `hooks.json` is wired for Antigravity, and `hooks/hooks.json` is never created at the repository root. On Antigravity, rely on repo-level git hooks (`python3 <runtime-root>/scripts/install_git_hooks.py`), explicit validator scripts, and the `/git-safety-check` workflow.

## Codex flow evidence and limits

`flow-order-guard-codex.mjs` allows a recognized source edit after either a same-work-id spec/plan pair written in this rollout and validated strictly, or a recorded invocation of a recognized test runner. A RED run counts for ordering: the pre-edit check deliberately does not require a successful test result. On-disk-only artifacts do not satisfy the pair; a single patch that bundles artifacts and source is not prior evidence. An unreadable rollout or unavailable validator fails open; a readable rollout with missing/unresolvable required artifacts can deny.

`flow-step-guard-codex.mjs` activates only when this rollout records a spec/plan write. It attaches spec/plan/test obligations only when a non-test source edit is also observed. Artifact checks use strict validation and same-work-id pairing. Test evidence requires a recognized runner invocation; `echo pytest` does not qualify. A correlated exit code 0 satisfies the result check; a nonzero exit does not. A missing exit code fails open to invocation-only evidence. Correlation uses `call_id`, first taking the recorded `function_call_output` exit line and then the structured `exec_command_end` fallback.

A correlated exit code counts only when it is attributable to the runner (BR6, default-on). The command is split into statements on unquoted `;`, newline and `||`. A command that holds `;`, newline or `||` and lies outside the safe shell grammar described under the limits below is not attributable. Otherwise real-runner attribution requires the runner to be the last statement: `pytest; echo EXIT=$?` and `pytest || true` lose attribution, and so does a trailing version-only or help-only runner such as `pytest; pytest --version` or `pytest; npm test -- --help`. In a trailing `||` run every operand must be a real runner, and every operand before the last must have no unquoted pipe and no background `&`. `&&` chains keep attribution (`cd repo && pytest`, `pytest && pytest --version`), because `&&` is not a BR6 split. Pipelines such as `pytest | tee log.txt` keep default attribution as a documented limit. A background job (an unquoted, unescaped `&` not joined to another operator) in the last statement keeps default attribution and is not attributable under strict evaluation (DP33). A standalone `pytest --version` stays default-accepted, and a run with no correlated exit code keeps the fail-open, invocation-only outcome.

Native Codex 0.154.0 WSL records successful patches as `custom_tool_call` / `custom_tool_call_output`, and shell exits as `Process exited with code N`. The reader retains historical carriers and accepts these current ones. It reads only leading native metadata before `Output:` or unknown text; tool-output or denial-echo headers are not exit evidence. A current custom patch needs its own correlated exit 0 and a success marker at the start of the actual output body. Missing, refused, failed, mismatched-type, or conflicting-call records do not count as successful patch writes. The captured fixture and mutations in `tests/test_codex_current_rollout.py` pin this boundary.

These checks do not establish test quality or freshness after the latest source edit: they scan the whole rollout, do not bind a test to one work id, and do not require a test-summary signature. A successful `pytest --version` can qualify. The parser also cannot guarantee that a runner-shaped segment in a compound shell command actually executed. Run and inspect the real final verification separately. The current allowlist includes `make test`, `npm test` / `npm run test`, yarn/pnpm test forms, `tox`, and `nox`, alongside direct Python/JS/Go/Rust/JVM runners; arbitrary shell scripts and unrecognized wrappers remain outside the invocation recognizer.

Flow evidence recognizes `apply_patch` targets, ordinary `>` / `>>` targets, and operands of `sed -i` and `tee`, including multi-file writes. The current-edit recognizer respects quotes, heredocs, expansion-dependent targets, and the actual tool name. The prior-write reader is broader and can over-approximate writes. Unrecognized copy/encoding commands without a recognized redirect, expansion-derived targets, source deletes, and extended/fd redirects (`&>`, `&>>`, `>|`, `N>`, `>&N`) remain bounded gaps. Recognizing a target for flow evidence does not mean its content is covered by the secret scanner: that scanner scans only literal added content from patch/printf/echo/heredoc forms. Arbitrary tee/base64/command-substitution output is not checkable by this layer and remains fail-open.

Other limits remain material:

- The rollout reader has an 8 MiB ceiling; literal write extraction has a 512 KiB bound. Missing, unreadable, or oversized inputs can suppress enforcement.
- Artifact-less refactors and implementation resumed with only prior-session artifacts do not activate the Codex flow-step backstop. `Skill` / `Workflow` / `Agent`-only security, control, and dispatch steps are not observed by this adapter. The pipeline's security and control steps are `Agent`-only (`security-reviewer`, `implementation-auditor`), so on Codex they are covered by the offline strict grader, not by a hook.
- Completion-claim patterns are narrow and English-only. The sentinel must appear in the final assistant message; prior quoted/user messages do not count. A model can still repeat the marker without good evidence, so its presence is not proof of correctness.
- Stop adapters check `stop_hook_active` to avoid repeated continuation. They use payload `cwd`, falling back to the hook process directory; unresolved artifact locations can prevent useful evidence. Missing/unreadable inputs fail open, but malformed JSONL lines are skipped: a still-readable partial rollout can lack evidence and trigger a flow-order denial.

### Limits of branch, review-result and strict evidence

The publication decision blocks in the [current release ledger](release-evidence-0.6.0.md), the [0.5.0 ledger](release-evidence-0.5.0.md) and the [0.4.3 ledger](release-evidence-0.4.3.md) link this section.

- The live Codex Stop hook does not report the `branch` step. The Codex branch report is the `strict_branch=protected|ok|unknown` line of the offline `scripts/strict_flow_evidence.py --rollout <path> --cwd <dir>`.
- Codex rollouts expose no reviewer dispatch event, so `review-result` is Claude-only.
- On Claude, `branch` observes the working-directory branch at Stop time. An edit made on `main` followed by a checkout of another branch is missed; `branch-guard.mjs` still covers commits and pushes. Both `branch` and `review-result` are warn-level steps and never block, under any flag.
- `AGENTIC_FLOW_STRICT_EVIDENCE` (`true`, `1` or `yes`, case-insensitive; default off) makes the live Codex `tests` evidence strict. Claude test evidence is judged strictly only by the procedure eval's `--strict-evidence`; the flag does not change the live Claude outcome.
- These properties are not observable by the hooks: the work-type core read before the first edit, whether the pipeline's `red-first` test run failed, the full pipeline step order, an approved (as opposed to schema-valid) spec or plan, reviewer independence, and re-review after a hook-definition change. The offline strict grader checks the core read (`core-read`), the failing run before the first production edit and the `required_order` sequence; the validator accepts `status: approved` but cannot prove who approved.
- Hook enforcement of the `agentic-sdlc-pipeline` steps beyond spec, plan and tests covers Claude Code only; the Codex flow-step Stop backstop checks only the merged spec, plan and tests steps. The `dispatch` step needs a `Skill` call to `dispatch-strategy`, and its `security` and `control` steps need `Agent` dispatches of `security-reviewer` and `implementation-auditor`, each matched by exact name (the name or `agentic-sdlc:<name>`). Its `red-first` step needs a test command before a production-source edit; it has no Stop key, so it never joins the Codex Stop gate. Codex is covered by the offline strict grader (`scripts/run_procedure_eval.py --strict-evidence`).
- Hook flow activation is by the `Skill` tool. A pipeline run started only by the `/agentic-sdlc-pipeline` slash command is covered by the offline procedure eval, not by the flow hooks.
- Codex wraps test runs in `/bin/bash -lc '…'`, and on Windows in `powershell -Command "…"`. The grader attributes neither wrapper as a test run, so the strict red/green checks (`require_red_green`, `red_before_source_edit`) cannot pass on real Codex transcripts. Codex acceptance is limited to the forbidden-skill, marker and reviewer-output checks.
- Windows hook support is worded as the current [Codex hooks page](https://learn.chatgpt.com/docs/hooks) states it, as captured 2026-09-14: a Windows-only `commandWindows` command override and a `windows_managed_dir` setting.
- The post-install check `scripts/check_codex_hook_trust.py` reports hook trust state from `hooks/list` only; it does not prove that a hook runs, that `node` is on PATH, or that a trusted hook has an effect.
- Exit attribution is lexical. An exit code is attributed only while the command stays inside a safe shell grammar: unquoted words, single quotes, double quotes without command substitution, plain `$NAME` parameters, word-start comments, backslash escapes, the separators `;`, newline, `||`, `&&`, `|` and `&`, simple redirections such as `> out.txt` or `2>&1`, and command words that are external programs or the builtins `cd`, `echo`, `export`, `pwd`, `true`, `false`, `:` and `set -euo pipefail`. Any other syntax or command word, for example `$(`, a backtick, `${`, `(`, `{`, `[[`, `<<`, `printf`, `test`, `[`, `unset`, `wait`, `eval`, `source`, `alias`, `hash`, `trap`, `exec`, `set -n`, an assignment to an integer-attributed variable such as `RANDOM` or `OPTIND`, or an `export` argument that is not a literal `NAME=value` or plain word, makes a command that also holds `;`, newline or `||` unattributable by default and makes every command unattributable under strict evaluation, so a legitimate `cd repo; pytest $(cat args)` or `source .venv/bin/activate; pytest` reports `tests` missing. Not detected by the live Codex hook, `AGENTIC_FLOW_STRICT_EVIDENCE`, `scripts/strict_flow_evidence.py` or the procedure eval's `--strict-evidence`: how the runner name resolves or behaves outside the command text, such as `PATH=b:$PATH; pytest` after writing `b/pytest`, a `package.json` test script or a function inherited from the shell profile; and, by default only, a command without `;`, newline or `||` such as `set -n && pytest`, which never runs pytest. (D23, DP35)
- Test-runner arguments are read the way bash reads them. An argument is compared after quote and backslash removal, and an unquoted `<`, `>` or `&>` ends a word, so `pytest --version>out.txt` is version-only. Only a `&&` segment that itself runs the test runner counts, so `echo pytest && pytest --version` reports `tests` missing. An argument with a `$` expansion, or one without `/` that holds a glob character or starts with `~`, counts as a possible version or help flag, so `cd repo; pytest $ARGS` and `pytest; pytest -k test_*` report `tests` missing. Only space, tab and newline separate words; every other character, including U+00A0, is part of a word. A Superpowers delivery read counts only when it is the single `cat` statement of its command and reads one literal canonical absolute path under `<CODEX_HOME or ~/.codex>/plugins/cache/`; any other form is Ambiguous. The offline `scripts/strict_flow_evidence.py` uses the `CODEX_HOME` of its own process, so a rollout captured elsewhere is graded with `CODEX_HOME` set to that capture's home. `git` and `node` are started only from an absolute path found in an absolute `PATH` entry, and never as batch files. (D25, DP37)

Per-package evidence persists to `docs/agentic-sdlc/<slug>/evidence/<work_id>.md` — per-package only (flat packages get no evidence), overwritten in place per run (single canonical file, last run wins), git-ignored, and with no validator (it never gates resolution; the flow guards on neither runtime activate on an evidence write). That evidence write is performed by the main pipeline finalize step, not the read-only `implementation-auditor` sub-agent.

Per-package plan change-detection runs as a filesystem scan, not a `git status` query: new generated plans can be git-ignored, so the resolver scans the filesystem; published plugin documentation is tracked separately.
