# agentic-sdlc — Google Antigravity Experimental Adapter

> Status: **Experimental adapter**. **Not a supported release target** (supported release targets remain Claude Code and Codex; see [`docs/runtime-adapter.md`](../docs/runtime-adapter.md) and [`docs/publication/multi-platform-distribution.md`](../docs/publication/multi-platform-distribution.md)). The native install, reinstall and uninstall of the built package and one headless turn were recorded with agy 1.5.14 on 2026-11-21 ([compatibility matrix](../docs/publication/compatibility-matrix.md#google-antigravity)); nothing else is claimed.

Sources, all read on 2026-11-21: the references bundled with the Antigravity CLI `agy` 1.5.14 (`build-plugins.md`, `subagents.md`, and the `agy-customizations` skill's `hooks.md`), the [workflows-to-skills migration page](https://antigravity.google/docs/migration/workflows-to-skills), and `agy` 1.5.14 runs in isolated profiles. A claim below without one of these sources is marked unverified.

## 1. Manifest (`.antigravity-plugin/plugin.json`)

agy reads the manifest in place at `<plugin-root>/.antigravity-plugin/plugin.json`; it takes precedence over a root `plugin.json`, so no root `plugin.json` is created (a root one would also reach Codex's portable-manifest loader). The schema `https://antigravity.google/schemas/v1/plugin.json` requires only `name` (kebab-case) and sets `additionalProperties`: `false`; its other properties include `displayName`, `description`, `version`, `logo`, `author`, `homepage`, `repository`, `license` and `keywords`.

This manifest carries `name`, `displayName`, `version`, `description`, `author`, `homepage`, `repository`, `license`, `keywords` and `logo` (`assets/logo.png`). `version` is one of the versioned manifests in `scripts/bump_version.py`, so `--check` fails when it differs from `VERSION` and a bump rewrites it. agy reads the version from this file; without one it fell back to `.claude-plugin/plugin.json` (probe, 2026-11-21).

## 2. Build, install, upgrade and uninstall

Build the package from the committed tree, extract it, and install the folder:

```bash
python3 scripts/build_release.py --output <zip> --antigravity
python3 scripts/build_release.py --verify <zip>
python3 -m zipfile -e <zip> <package-dir>
agy plugin validate --json <package-dir>
agy plugin install <package-dir>
```

`agy plugin install` takes a folder, not a `.zip`, and copies it into `~/.gemini/config/plugins/agentic-sdlc/`. The package holds `.antigravity-plugin/plugin.json`, a root `hooks.json` (a copy of [`.antigravity-plugin/hooks.json`](hooks.json)), a root `mcp_config.json` (a copy of [`.antigravity-plugin/mcp_config.json`](mcp_config.json), the read-only search server), the hook launcher and the handlers it starts, the 16 skills, `contracts/`, `scripts/`, `flows/`, `assets/`, the roles as agy agents in `agents/`, the docs and workflow file the skills name as `<runtime-root>/...`, this README and `LICENSE`. It holds no `commands/`, `rules/`, `cursor/` or other runtime's manifest or hook wire.

- Upgrade: build the new version and run `agy plugin install <package-dir>` again; it replaces the installed folder. There is no `agy plugin update` in agy 1.5.14 (`agy update` updates the CLI).
- Uninstall: `agy plugin uninstall agentic-sdlc`. Unrelated files in the profile stay.
- A workspace-only install is the same folder at `<workspace>/.agents/plugins/agentic-sdlc/`.
- agy loads only the first 24000 bytes of a `SKILL.md` body. `agy plugin validate` (agy 1.5.14, probes 2026-11-22) counts the bytes after the closing frontmatter line, surrounding whitespace trimmed: 24000 passes, 24001 warns, and a three-byte character counts three. The build therefore splits any body over 24000 bytes in the package only (the shared skill is unchanged for every other runtime): `SKILL.md` keeps its frontmatter, opens with a read-first note naming `skills/<skill>/SKILL-continued.md` and the section it continues from, and keeps the leading whole sections; the rest moves byte for byte into `SKILL-continued.md` in the same folder, so relative links still resolve. Cuts fall only at headings outside code fences, at the shallowest level that fits; a body that cannot be cut, or a skill that already has a `SKILL-continued.md`, fails the build. Today this splits `skills/agentic-sdlc-pipeline/SKILL.md` (body 40735 bytes) before `## At kickoff (always)`, and `agy plugin validate --strict --json` on the package exits 0. In a live headless turn (2026-11-22) agy loaded the skill, ran `read_file` on `SKILL-continued.md` and quoted the `## Finalize` sentence that lives only there.

## 3. Roles as agy agents

`scripts/project_roles.py --target antigravity` generates `agents/<role>.md` from the shared `agents/*.md` at build time. agy skips an agent whose `tools` is a comma string, so each generated agent has a YAML-list `tools` of agy runtime names (`Read`/`Glob`/`Grep` -> `read_file`, `WebFetch`/`WebSearch` -> `search_web`, `Write` -> `write_file`, `Edit`/`MultiEdit` -> `edit_file`, `Bash`/`PowerShell` -> `run_command`), `model: inherit`, `subagent: true` and `mainAgent: false`. A read-only role (no write or shell tool) also gets `inheritMcp: false`. The body is the shared role body, byte for byte. `agy plugin validate` reports 11 agents.

agy has no grep, glob or directory-list tool, so the package bundles a read-only search MCP server, [`scripts/agy_search_mcp.py`](../scripts/agy_search_mcp.py) (stdlib Python 3, `python3` on `PATH`), registered in the root `mcp_config.json` as `search`; agy names it `agentic-sdlc_search`. Its tools are `grep` (a literal or a Python regular expression, one line at a time, an optional workspace-relative path glob, `max_results` up to 500) and `glob` (a workspace-relative glob). It searches only the workspace folders agy sends in answer to the MCP `roots/list` request (agy starts the server in the plugin root, so that folder is never the default), does not follow directory links, skips a file whose resolved path leaves the workspace, binary files, files over 2 MiB, `.git` and `node_modules`, refuses `..` and absolute globs, stops a regular expression after 10 seconds in a child process it kills, and caps its reply. It writes nothing.

How a role reaches it was measured, not assumed (agy 1.5.14, live probes 2026-11-22): every plugin subagent gets `call_mcp_tool` and the plugin's own MCP servers, even with `inheritMcp: false`; `call_mcp_tool` listed in `tools` stops the subagent from starting ("tool \"call_mcp_tool\" not found in registry", which `agy plugin validate` does not catch); `mcpServers` in agent frontmatter is ignored. So the projection grants neither, and read-only roles keep `inheritMcp: false` and no write or shell tool. In a live turn the read-only `code-reviewer` found a planted string with `call_mcp_tool` `agentic-sdlc_search`/`grep` and reported that it had no tool to create a file. The runtime also gives every subagent `manage_task`, `send_message`, `list_resources` and `read_resource`; `manage_task` can send input to a running terminal task, so a read-only role can still type shell input into a task that another agent left running; its `Input` goes through the command guards (section 4), which refuse only their patterns (destructive or protected-branch git, a commit with a secret), not writes in general. "No write or shell tool" means no `write_file`, `edit_file` or `run_command`; the live proof below ran with no terminal task open. Headless `-p` runs deny MCP calls that have no permission rule; a session can allow the search server with `--settings '{"permissions":{"allow":["mcp(agentic-sdlc_search/*)"]}}'`.

## 4. Hooks

The root `hooks.json` is one named group, `agentic-sdlc`. agy runs each command with `sh -c` (`cmd /c` on Windows, unverified here) in the folder that holds `hooks.json` and exports `PLUGIN_ROOT`, so the commands are relative: `node ./hooks/agy-launch.mjs --event <event> --handler <file>`.

| Event | Matcher | Shared handler |
|---|---|---|
| `PreToolUse` | `run_command\|manage_task\|run_workflow` | `scan-commit.mjs`, `destructive-command-guard.mjs`, `branch-guard.mjs` |
| `PreToolUse` | `write_file\|edit_file` | `scan-write.mjs` |
| `PreToolUse` | `*` (every other tool) | `scan-tool-args.mjs` |
| `SessionStart` | — | `session-start.mjs` |
| `Stop` | — | `worktree-scan.mjs` |

`hooks/agy-launch.mjs` reads the payload's `toolCall.name` and `toolCall.args` (`CommandLine` for `run_command`; `Input` for `manage_task`, whose `send_input` action types into a running terminal task, while an action without `Input` such as `status` or `kill` runs nothing; `Script`, or the file `ScriptPath` names, for `run_workflow`; `Path` with `Content` for `write_file`; `Path` with `Replacement` for `edit_file`; the shapes come from capture hooks in throwaway workspaces, 2026-11-21 and 2026-11-22, and subagent tool calls run the same hooks) and the payload `cwd` (else `workspacePaths[0]`; a tool call whose payload names neither is denied, because the hook's own folder is the plugin root). A `run_command` `Cwd` argument (listed in the web docs, not sent in the 2026-11-21 capture) names the folder the guards check, resolved against the payload `cwd`; a `Cwd` that is not a string or names no folder denies the call; `run_workflow` takes a `Cwd` the same way. Every tool that neither runs a command nor writes a file (`send_message`, `invoke_subagent`, `define_subagent`, `schedule`, `swarm`, `call_mcp_tool`, `search_web`, `ask_question` and any tool agy adds later) goes to `scan-tool-args.mjs`, which scans every string in the arguments, nested values and object keys included, with the high-confidence secret rules and denies on a finding, naming the rule and the argument path but never the value (an object key that is not a plain name, a token used as a key for example, is reported by position as `<key N>`, and a key is scanned whatever its value type); arguments over 4 MiB of text or nested deeper than 64 levels are denied too. `run_workflow` runs a Python script the shell guards cannot fully check, so its no-objection answer is `ask`, not `allow`, from every group, the `*` group included so no group approves it (live, headless agy 1.5.14, 2026-11-22: that `ask` does not hold the call by itself; agy's own command permission decides, so it was denied with no allow rule and ran with a matching `permissions.allow` rule, while a guard's deny of a script line still blocked it); a `ScriptPath` that is not a regular file (a FIFO, a device, a folder) is denied without being read. In a live headless turn (2026-11-22) a synthetic test token in an `invoke_subagent` `Prompt` and in a `send_message` `Message` was denied, and `manage_task` `send_input` of `git reset --hard` was denied by the destructive-command guard. The launcher hands the shared handler the Claude-shaped input it already reads, and prints one JSON object: a deny becomes `{"decision":"deny","reason":...}`, a write-scan or argument-scan finding becomes a deny, a shell guard's warning (a protected branch, a skipped scan) becomes `{"decision":"ask","reason":...}`, and a call the guards have nothing to say about `{"decision":"allow"}`. A PreToolUse guard that crashes, times out or prints something other than a JSON object denies the call, and so does a tool call whose `CommandLine`, `Path`, `Content` or `Replacement` is missing or not a string, a `manage_task` `Input` or `run_workflow` `Script` that is not a string, or a `run_workflow` script that cannot be read. agy blocked the call on exit status 2 and on invalid JSON from a PreToolUse hook (one probe each, 2026-11-21), while agy's bundled `build-plugins.md` says a non-zero exit is logged and ignored (fails open); other exit codes are unverified, and the launcher relies on neither. SessionStart injects the bootstrap as `injectSteps` `systemMessage`; Stop continues the agent only when `AGENTIC_WORKTREE_SCAN_BLOCK` is set, the scan finds a secret and `continuationActive` is not `true`. Payload text never reaches a shell.

Trade-offs and gaps of this wiring (agy 1.5.14, 2026-11-21):

- **`allow` is the only no-objection answer.** agy's `hooks.md` defines `"allow"` as "Automatically allow the tool execution" and `"ask"` as a permission prompt. There is no neutral answer: in a probe, a PreToolUse hook that printed `{}` made agy deny the `run_command` ("tool call denied by pre-tool hook"). So the launcher answers `allow` only when the guards have nothing to say. A warning never approves: the write scanner's finding denies the write and a shell guard's warning answers `ask`, as on Cursor. In headless `-p` probes, that `allow` did not override a user's `permissions.ask` rule (the call was still auto-denied because no prompt was possible) or `permissions.deny` rule (still "Permission denied ... deny rule"). Whether `allow` skips a prompt that agy's interactive default policy would show was not tested; treat that as unverified. To keep a confirmation step on agy, add `permissions.ask` or `permissions.deny` rules in agy's `settings.json`.
- **The hook payload does not name the calling agent** (capture 2026-11-22), so a hook cannot limit a read-only role to the search server; a role can call any MCP server its plugin context exposes. The argument scan still applies to those calls. For the same reason a read-only role's `manage_task` `send_input` into a running terminal task is checked only by the command guards.
- **The default Stop advisory is dropped.** Without `AGENTIC_WORKTREE_SCAN_BLOCK`, `worktree-scan.mjs` answers a finding with a `systemMessage` advisory. agy's Stop output only injects `reason` on `continue`, so on agy that advisory reaches nobody and the launcher answers `{}`. Set `AGENTIC_WORKTREE_SCAN_BLOCK=true` on agy to hear about a finding (one continuation per turn).
- **Live hook delivery was seen only for a workspace plugin** (`<workspace>/.agents/plugins/agentic-sdlc/`). Hooks of a plugin installed with `agy plugin install`, and the Stop path, were not exercised in a live turn.

Not wired: the flow-order guard and the completion-claim and flow-step Stop readers, which read a Claude transcript and Claude `Skill`/`Agent` tool events that agy does not produce. `PostToolUse`, `PreInvocation` and `PostInvocation` are not used.

## 5. Runtime capabilities on Antigravity

| Capability | Antigravity mechanism | Adapter behavior |
|---|---|---|
| Session router (`using-agentic-sdlc`) | SessionStart bootstrap, the skill catalog, `/using-agentic-sdlc` | The bootstrap names the router; read the selected `SKILL.md` with `read_file` before acting. |
| Plugin root (`<runtime-root>`) | Two levels above the loaded `SKILL.md` | Verify `<runtime-root>/scripts/validate_artifacts.py` exists and pass that quoted absolute path to `python3` (`py -3` on Windows). `PLUGIN_ROOT` is set for hook commands (and plugin MCP servers); it is not substituted in skill text. |
| Specialist subagents | `invoke_subagent` | Use the bundled agent of the role, or pass the body of `<runtime-root>/agents/<role>.md` (frontmatter stripped) to a built-in subagent. Name the files a read-only role must read; it can also search with `agentic-sdlc_search` (`grep`, `glob`) through `call_mcp_tool`. If `invoke_subagent` is unavailable, run inline and record `Delegation Degraded: subagents unavailable (single-session inline fallback)`. |
| Workflows (`spec-plan-draft`, `multi-lens-review`, `skill-draft`) | Embedded author -> critic -> revise via `invoke_subagent` + `validate_artifacts.py` | Antigravity `.agents/workflows/*.md` prompt macros are deprecated (no removal date announced) and are not Claude Code's JS `Workflow` runtime; no `.agents/workflows/` file is used. |
| Commands | — | `commands/` is not shipped: agy reported converting `git-safety-check` to a skill on install, but no such skill folder appeared and its use in a session is unverified. Known gap: the pipeline's read-only `git-safety-check` step has no installed command on agy. |
| Artifact and evidence paths | Dual layout under `docs/agentic-sdlc/` | Unchanged; change detection uses `resolve_work_package.py`. |
