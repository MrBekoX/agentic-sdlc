# lessons.md — verified, durable lessons for agentic-sdlc

Append a lesson only after a **verified** failure or wrong solution that you have reproduced, fixed, and root-caused — and only when the lesson is general enough to prevent similar mistakes in future work. Prefer enforcing each rule with a test, schema, linter, or hook over relying on this prose.

Review relevant entries before starting similar work. Keep newest entries at the top.

**Do not record:** transient network/tool errors, unverified guesses, secrets or machine-specific data, or duplicates of an existing lesson.

## Entry schema

Each entry includes:

- **Date** — `YYYY-MM-DD`
- **Task / context** — what was being done
- **Symptom** — the observable failure
- **Root cause** — the underlying reason
- **Correct fix** — what actually resolved it
- **Preventive rule / automated check** — what stops recurrence (ideally enforced)
- **Related files & tests** — paths to the change and its coverage

## 2026-09-21 — "Some error was recorded" is a weaker claim than "this error was recorded", and the mutation is what tells you which one you wrote

- **Task / context:** Strengthening ten assertions that an audit found could not fail - whole-file keyword greps, a floor of 40 over 72 rows, a JSON round-trip of a value against itself, a `git ls-files` in a repo where nothing was ever staged, a substring that another word satisfied.
- **Symptom:** Two of the ten strengthened rows STILL could not fail, and only the mutation run said so. F3 replaced `assertEqual(errors, sorted(errors))` - true because the function returns `sorted(errors)` - with `assertTrue(errors)`. Silencing the `invalid_polarity` membership check left `polarity_split` and `missing_field` behind, so "some error" was still satisfied and the row stayed green while a check had been deleted. F5 replaced a substring test with a word-boundary one, correctly; the MUTATION was the incomplete part, deleting the word from one of the two documents the assertion concatenates, so the other still satisfied it.
- **Root cause:** Two different mistakes that look identical from the green bar. F3 was a fix that was stronger than before but still weaker than the property it named. F5 was a correct fix with a mutation that did not actually introduce the defect. Without running the mutation, both read as "done" - which is exactly the state the ten original assertions were in.
- **Correct fix:** F3 asserts the EXACT set of error-label prefixes per field, measured across the full 11x5 hostile-value matrix rather than written from reading the function; silencing one check changes the set. F5's mutation was widened to both documents. Ten of ten now go red under the defect each names, with every file restored byte-for-byte and the restoration checked by digest - including the two the content harness could not express, where the defect is a renamed DIRECTORY and a per-run writer rather than an edit.
- **A third thing the matrix showed:** measuring instead of assuming changed the finding itself. The first attempt required every field to record a label and failed 21 of 55 combinations - my assumption, not the function's contract, which promises that every MEMBERSHIP check records a label and that nothing raises. The real gap turned out to be exactly 8 combinations in two free-text fields whose only check is `if not case.get(field)`, so a truthy non-string passes. Recorded in the expected-label map rather than silently widened, because other rows depend on that helper's current behaviour.
- **Preventive rule / automated check:** After strengthening an assertion, write the mutation that introduces the defect the assertion NAMES and require red - and when it stays green, ask which of the two things happened before touching anything: the fix is too weak, or the mutation is too small. They need opposite responses, and guessing wrong makes the next round worse. Where a claim has a shape ("records a label", "enumerates these forms"), assert the exact shape; a non-emptiness test is satisfied by a neighbour's output.
- **Related files & tests:** `tests/test_skill_integration.py` (section-scoped Workflow rule), `tests/skills/harness.py` (`_shipped`), `tests/test_skill_fixtures.py` (`FIELD_ERROR_PREFIXES`), `tests/test_br6_case_table.py`, `tests/test_codex_write_guard.py`, `tests/test_evidence_tracking_gate.py`, `tests/test_evidence_persist.py`, `tests/test_sensitive_redaction.py`, `tests/test_packaging_metadata.py`, `tests/test_house_voice.py`.

## 2026-09-21 — When a reported key names something narrower than the command that produced it, both the label and the cost are wrong

- **Task / context:** Auditing the local gate. `scripts/check_all.py` ran `unittest discover -s tests` with the default pattern. Its comment said *"Run the deterministic-validator unit tests"*, its variable was `tests_ok`, its error was `validator_tests_failed`, and its output line was `validator_tests=pass`. AGENTS.md documents the script as "skill frontmatter + validator tests".
- **Symptom:** The default pattern collects every suite - 49 files, ~1300 tests. So three things were true at once and none of them was visible from the output: `validator_tests=pass` reported the result of the ENTIRE suite; the documented four-command gate collected that suite twice, because its fourth command is the same discover; and `.pre-commit-config.yaml` runs this script, so every commit silently paid a full suite run. Measured here: 440 s for the suite, 1.3 s restricted to the validator, 3.0 s for the whole narrowed script. In CI the duplication multiplied - four full runs per OS, eight per trigger - and the workflow's own comment, which said "the gate runs the suite twice", undercounted by 2x because it counted only the explicit steps.
- **Root cause:** One line grew wider than its label and nothing forced the two to agree. A `key=value` line is a claim about what was measured, and an unrestricted discover is the easiest way to make that claim quietly false - it does MORE, not less, so nothing fails and nobody looks. The cost hid in the same place: work that duplicates other work never shows up as a failure, only as time, and time gets attributed to "the suite is big" rather than to running it twice.
- **Correct fix:** Name what is run. `VALIDATOR_TEST_PATTERNS` lists the suites, the script runs those, and `tests/test_gate_composition.py` fails if the unrestricted form returns or if a named pattern matches no file. The coverage risk of narrowing a gate command is handled by pinning the premise, not the conclusion: a test asserts that every `tests/test_*.py` is still collected by a documented gate command AND that AGENTS.md still documents a full-suite command - narrow one further without moving its files and that goes red. The output gained a `suites_not_run_here` line, because a contributor reading only this script's output should not have to infer what it skipped.
- **The trade that comes with it, named rather than buried:** `pre-commit` is now fast, which means a commit can land locally without the full suite. That is deliberate, and the reasoning is one this repository already recorded - a guard that blocks routine safe work for eight minutes gets switched off, and a disabled guard covers nothing. The suite stays mandatory in the documented gate and in CI, and `docs/testing.md` says so where a contributor reads it instead of leaving it to be inferred.
- **Preventive rule / automated check:** For any tool that prints a result key, ask what command produced it and whether the key names exactly that. Where the answer is "a discover with a default pattern", it almost certainly names less than it ran. Two cheap pins: name the inputs in a constant a test can read, and assert that nothing fell out of the gate as a whole when one command is narrowed.
- **Related files & tests:** `scripts/check_all.py` (`VALIDATOR_TEST_PATTERNS`, `suites_not_run_here`), `.pre-commit-config.yaml`, `.github/workflows/ci.yml` (comment corrected; source checkout given `fetch-depth: 0` so the historical-ledger pin stops skipping on every CI job), `docs/testing.md`; `tests/test_gate_composition.py`.

## 2026-09-21 — A gate that is weaker than the check downstream is a false green, not a gate

- **Task / context:** Authoring a plan for another package in this repository. `skills/plan-authoring/SKILL.md:55` tells the author to run `scripts/validate_artifacts.py --mode plan ... --strict`, and `skills/agentic-sdlc-pipeline/SKILL.md:130` states that a non-zero exit from it BLOCKS the gate. The plan validated clean.
- **Symptom:** Minutes later the full suite failed on that same file with `plan_missing:branch`. `scripts/resolve_work_package.py`, which runs later at implementation time, requires `work_id`, `spec`, `branch` and `status` on a plan and rejects the artifact outright when one is absent. `validate_artifacts.py` parsed no frontmatter AT ALL - it had no such code - so the tool advertised as the deterministic gate was blind to a rule the pipeline enforces unconditionally a step later.
- **Root cause:** The rule existed in three places and was enforced in one. `plan-authoring/SKILL.md:54` documents the four keys in prose; the resolver enforces them; the gate did not. Nobody had compared the two tools' notions of "valid", because each looked correct on its own. The failure only appears at the seam, and the seam is exactly where a workflow says "this check means you may proceed".
- **Correct fix:** Teach the gate the same frontmatter, as ERRORS rather than warnings promoted by `--strict` - a key whose absence is unconditionally fatal downstream is not a style preference, and labelling it a warning is the same mislabelling in a smaller font. The validator still does not IMPORT the resolver: it is invoked standalone from the skills on both runtimes and must not acquire the resolver's git and filesystem behaviour, so the constants are mirrored and `tests/test_validator_resolver_parity.py` pins them equal - mutation-verified by dropping one key from one script and requiring red. Path semantics stayed with the resolver on purpose: checking where `spec:` POINTS needs a repository root the validator does not take.
- **A second lesson inside the first:** the fixtures carried no frontmatter, so fixing the validator turned six of them red. Giving them real frontmatter - rather than exempting them - then silently broke two of the NEW rows, which had been written on the assumption that a fixture had no frontmatter block. A fixture change can invalidate the premise of a test that reads it; after changing shared fixtures, re-read every test that depends on the property you changed, not just the ones that go red.
- **Preventive rule / automated check:** When a workflow advertises one tool as the gate for a rule that another tool enforces later, compare their notions of valid and pin them with a test. The gate must be at least as strict as the downstream check, or it is a false green that only defers the failure to a point where the work is already done. Where the two tools cannot share code - a standalone CLI that must not take on a heavier dependency - mirror the constant and let a parity test carry the guarantee.
- **Related files & tests:** `scripts/validate_artifacts.py` (`FRONTMATTER_REQUIRED`, `parse_frontmatter`, `check_frontmatter`), `scripts/resolve_work_package.py` (unchanged - it was already right); `tests/test_validate_artifacts.py::TestFrontmatterRequirements`, `tests/test_validator_resolver_parity.py`.

## 2026-09-21 — A claim with no mechanism drifts until it is false; bind the claim, not the prose

- **Task / context:** Auditing `docs/testing.md`, the document a contributor reads to learn what the gate proves. Two defects turned out to share one cause.
- **Symptom A - the promise the code contradicts:** four places (the doc's gate table, its suite-map row, its troubleshooting table, and `tests/test_static_node.py`'s own docstring) promised that the static JavaScript checks SKIP when `node` is absent - the troubleshooting row says it outright: *"the test skips rather than passes."* `TestWorkflowSyntax` carried no skip decorator and called a helper that runs `subprocess.run([NODE, ...])`; with `NODE is None` that raises `TypeError`, so a missing interpreter turned a promised skip into a red gate. The inverse held too: the one class that needs no `node` at all - it only reads bytes - WAS decorated, so it was skipped for a reason that did not apply to it.
- **Symptom B - the inventory that quietly stopped being one:** the Test suite map introduces itself as the suite's organisation ("each concern has a dedicated suite") and listed 21 rows for 49 files. The largest security suite and the only file carrying harness negative controls were both absent. Nothing went wrong at any single moment; rows simply were not added as files were.
- **Root cause:** In both cases a claim was stated in prose and enforced by nothing. Prose cannot notice when it stops being true, and nobody re-reads a paragraph to check it against 49 files. A decorator per class has the same weakness one level down - it relies on the next author remembering.
- **Correct fix:** Put the guarantee where forgetting is impossible. The skip now lives in the HELPER (`_node_check` raises `SkipTest` when no interpreter is available), so a class added later that forgets the decorator degrades to the promised skip instead of a red gate; the decorators stay because they skip without paying a subprocess, and the byte-level class lost its irrelevant one. The map is now pinned by `tests/test_testing_doc_map.py`: every suite has a row, no row names a deleted file, and every deliberate exclusion carries a written reason. Mutation-verified in both directions - a phantom suite with no row goes red, a row whose file is gone goes red.
- **The limit, stated rather than implied:** the map test is a DRIFT gate, not a truth gate. It knows a row exists; it cannot know the row is accurate. So the 28 added rows were each written from the suite's own docstring, class names and test names, and the test's docstring says plainly what it cannot check. A test that quietly implied more would be the same defect in a new place.
- **Preventive rule / automated check:** When a document states a fact about the code - an inventory, a count, a behaviour under some condition - ask what would fail if it stopped being true. If the answer is "a reader might notice", write the check. Two shapes cover most of it: for an inventory, assert set equality against the tree with a named exclusion list; for a promised behaviour, move the promise into the narrowest function every path goes through.
- **Related files & tests:** `tests/test_static_node.py` (`_node_check` guard, `TestMissingNodeIsASkipNotAnError`), `tests/test_testing_doc_map.py`, `docs/testing.md` (suite map, CI trigger, gate table).

## 2026-09-21 — A lock that re-reads its expected value from the moving baseline is not a lock

- **Task / context:** Auditing the test suite for assertions that cannot fail. Seven of them claimed to pin a regression surface byte-for-byte by comparing a working-tree file against `git show HEAD:<path>`. Four covered guard files; three covered hook-wiring JSON. The surrounding prose was emphatic - a heading reading `the FULL regression surface stays byte-identical`, a class named `TestRegressionSurfaceUntouched`, and a comment asserting that a named rename was `the only permitted delta`.
- **Symptom:** On a clean checkout the working tree IS `HEAD`, so the content half of every one of those assertions reduced to `content == content`. `.github/workflows/ci.yml` checks out and runs nothing that writes into the tree before `unittest discover`, so in CI they were in the always-passing state by construction. Demonstrated in a scratch repository: clean checkout passes; an uncommitted edit fails - the ONLY window the shape fires; the same edit, once committed, passes again with a `BACKDOOR` line sitting inside the locked guard. And it had already happened here: commit `c173b99` changed `hooks/flow-step-guard.mjs` and `hooks/completion-claim-guard.mjs`, both locked, and in the SAME commit added a string-replacement hatch to neutralise the lock it had just tripped. That string now occurs nowhere, so the hatch became a permanent no-op wrapped around a tautology.
- **A second shape in the same cluster:** three of the seven filtered a handler list by name on BOTH sides and compared the results. Deleting the handler they guard made both sides `[]`, so `assertEqual([], [])` passed. Removing the thing a lock protects made the lock green.
- **Root cause:** The expected value was DERIVED at run time from a baseline that moves with the thing being checked. A lock is only a lock when its expected value is fixed independently - and when changing it is a visible act. The repository already contained the correct shape a few files away (`tests/test_codex_write_guard.py` pins two files by LF-normalized sha256 literal, and commit `c043c31` was forced to bump that literal in the same commit that changed the file), so this was not missing knowledge; the two shapes simply never got compared.
- **Correct fix:** Whole-file locks became LF-normalized sha256 literals with a per-entry rationale; structural locks became pinned literals with PRESENCE asserted before the comparison, so removal fails. The escape hatch went with them. Every converted lock was then mutation-verified - 13 expectations, each file mutated with a behaviour-preserving byte change, the row required to go red, the file restored and the restoration checked by digest. A meta-test now pins the property rather than any file: no live test may resolve an expected value from `git show HEAD:`, and every locked path's expected value must appear as a literal in the test source, so a digest recomputed at run time cannot quietly reintroduce the tautology.
- **Preventive rule / automated check:** For any assertion described as a lock, pin, golden or "unchanged", ask ONE question: where does the expected value come from, and does it move when the thing under test moves? If it is read from HEAD, from the same function under test, or recomputed from the same input, it is a tautology however emphatic the comment beside it. The check is cheap and mechanical - assert that the expected value is a literal in the source. And never accept a lock nobody has watched fail: mutate the file it names, require red, restore by digest.
- **Related files & tests:** `tests/test_byte_lock_integrity.py` (the property); `tests/test_codex_flow_order_guard.py`, `tests/test_codex_flow_step_guard.py`, `tests/test_codex_completion_claim_guard.py` (converted locks and pinned wiring literals); `tests/test_codex_write_guard.py` (the working reference, digests hoisted to module scope so the meta-test can see them).

## 2026-09-18 — A patched seam the code no longer uses makes a test assert the environment

- **Task / context:** The first two-OS CI run of the publication-readiness branch. Both platforms failed; neither failure was reproducible on the development machine.
- **Symptom:** `test_live_run_stops_before_model_on_git_failure` patched `procedure_eval.shutil.which` and asserted a fixture-git error, but CI reported `error=claude CLI missing`. Separately, Windows CI failed `test_codex_home_resolution` with `None != 'C:/Users/RUNNER~1/.../.codex'`.
- **Root cause:** Two different shapes of the same blindness. (1) A security fix (SEC-8) moved the bare-name CLI lookup off `shutil.which` onto an absolute-PATH scan, so the test's patch became inert and the real PATH decided the result: it passed locally only because a `claude` binary happened to be installed. (2) `hooks/codex-rollout.mjs` excluded `~` from its literal-absolute-path pattern, so `resolveCodexHome` returned null for every Windows 8.3 short name — a real product bug, invisible locally because this machine's temp path is a long name.
- **Correct fix:** Patch the seam the implementation actually calls (`resolve_agent_cli`) and assert against the stub it returns, so the test no longer depends on what is installed. Accept `~` inside the path pattern: it is a literal there, and leading-`~` expansion cannot apply because the pattern already requires the path to start with `/` or a drive letter. RED test first in both cases.
- **Preventive rule / automated check:** When a change moves a lookup, grep the tests for patches of the OLD seam — an inert patch does not fail, it silently hands the assertion to the environment. And treat a green local gate as evidence about one OS with one set of installed binaries: keep the two-OS CI matrix in the required set, because path shapes (8.3 short names, case folding, separators) and absent binaries only appear there.
- **Related files & tests:** `scripts/run_procedure_eval.py` (`resolve_agent_cli`), `tests/test_procedure_eval.py::TestFixtureGitFailure`, `hooks/codex-rollout.mjs` (`LITERAL_ABSOLUTE_PATH`), `tests/test_codex_completion_claim_guard.py::TestOwnerSignalScanner::test_codex_home_resolution`.

## 2026-09-18 — A run that never happened is not a failed run

- **Task / context:** Publication-readiness live evidence. The one maintainer-approved Claude file-tool sentinel probe was made; the CLI could not authenticate, answered with its own `<synthetic>` message, billed nothing, and never started a model turn.
- **Symptom:** `probe_check.py` classified the record `claude_file_sentinel=failed:no_write_attempt,model_mismatch` / `blocked:probe_failed`, which reads as "Claude was asked to write into the capture area and attempted nothing" — a statement about sandbox behaviour that the evidence does not support. `fill_ledger.py` then rendered the same false reading into the release ledger ("no native refusal was observed, so the AC78 prerequisite was not met"), and its reason rule rejected the honest not-run row because the text carried none of the accepted tokens.
- **Root cause:** Both classifiers had exactly two outcomes for an unsuccessful call — passed or failed — so every environment failure was funnelled into the failure vocabulary of the thing under test. The evidence needed a third state that distinguishes *the run happened and failed* from *the run never happened*.
- **Correct fix:** A fail-closed `not-run:no_model_turn` classification requiring every one of: only `<synthetic>` assistant model ids, no `tool_use`, an error result, zero cost, and no approval violation — a real model id, any tool call, a non-error result or any spend keeps the failure verdict. The record gained `assistant_model_ids`, re-derived from the kept stream without repeating the paid call. The ledger row now states that the call never reached the model, that the prerequisite could not be evaluated in either direction, and that the runtime is halted.
- **Preventive rule / automated check:** A tool that grades a live run must be able to say "this run never happened", and that state must be *earned* by positive evidence, never inferred from the absence of a success signal — otherwise an expired session, a missing binary or a network fault is published as a product or security finding. Pair every such classifier with fail-closed twin controls (real model id, billed run, unapproved command) that must stay `failed`.
- **Related files & tests:** `tests/artifacts/publication/tools/probe_check.py` (`no_model_turn`), `tools/fill_ledger.py` (Claude procedure row), the fourteen Task 136 probe controls, and plan decision D32.

## 2026-08-23 — When a layer is provably incomplete, add a layer; do not keep patching it

- **Task / context:** After ten adversarial rounds hardened the PreToolUse command guards, the loop was still producing real findings. The remaining gaps were not bugs — they were the layer's definition.
- **Symptom:** Every surviving bypass shared one shape: something the SHELL resolves after the hook has already decided. A shell function named `gc` wrapping `git commit`; `eval "$(printf 'git com'; printf 'mit')"`; `C=commit; git $C`; and writes through `tee`, `base64 -d` or `python -c` — none of which a command-string reader can see, and no amount of parser work changes that. Patching harder was producing narrower and narrower fixes (a mid-name `.pub.`, a `printf` octal escape) while the structural hole stayed open.
- **Root cause:** The guard was installed at the wrong altitude. A PreToolUse hook receives a STRING and must predict an EFFECT; deciding what an arbitrary shell command does is undecidable, so the layer can only ever be a probabilistic backstop. Ten rounds of fixes raised its recall — they could not change its category.
- **Correct fix:** Add layers that observe the effect instead of predicting it. Git runs `pre-commit` / `pre-merge-commit` / `commit-msg` / `prepare-commit-msg` on the OPERATION, after it has resolved its own alias table and the shell has done quote removal and `$PATH` lookup; a Stop-time scan reads bytes on disk, so the write form is irrelevant. Both reuse the SAME hardened detection primitives, so the ten rounds' work carries over untouched — the new layers add reach, not a second scanner to keep in sync. Measured result: 12/12 of the previously-unreachable techniques are now caught, controls still clean.
- **Preventive rule / automated check:** Before hardening a guard for another round, ask what LAYER it sits at and whether the residuals are bugs or definitional. If the residual list is "everything the runtime resolves after we decide", stop patching and add an observation point lower down. Then state each layer's limit in its own file header — `--no-verify`, `core.hooksPath=/dev/null`, `Stop` not firing on user interrupt — and pin them with tests, so the layering is never mistaken for completeness. ## 2026-08-23 — Enumerate the decoding layers between the string you inspect and the bytes that land

- **Task / context:** Rounds 5–9 of the adversarial loop over the PreToolUse guards. The loop ran until each round's findings were exotic rather than routine; 22 distinct defects were closed across nine rounds.
- **Symptom:** After the obvious bypasses were closed, every remaining one was a TRANSFORMATION the guard did not model — the command string it reads is not the bytes that reach the sink:
  - `git commit -m $'\x73\x6b...'` — bash ANSI-C quoting is decoded by the shell; history records `sk-...` while the guard reads `$'\x73...'`.
  - `$'\x67\x69\x74' commit` — the same trick applied to the COMMAND NAME, which slipped past the cheap `\bgit\b` pre-filter that ran before decoding.
  - `printf '\163\153\137...' > f` — POSIX printf decodes backslash escapes in its FORMAT string unconditionally (no `-e` needed), and `echo -e` does the same; the file gets `sk_live_...` while the extractor saw `163153137...` and still reported `parsed:true`.
  - `git commit -am"<secret>"` — git bundles short options, so the message token starts with `-a`, not `-m`.
- **Root cause:** A guard that reads `tool_input.command` sits ABOVE several independent decoders — the shell's quoting rules, git's own option bundling and alias table, and the invoked program's own escape processing (printf's format string). Each is a separate layer, and modelling one says nothing about the others. Closing "the quoting bug" three times in three different layers is the symptom of not having enumerated them.
- **Correct fix:** Decode what is decodable and scan a UNION rather than a replacement — the raw text AND its decoded form, so a decoder that is wrong or incomplete can only add detections, never remove one. `hooks/shell-quoting.mjs` centralises ANSI-C decoding; `payloadText` + `stripQuoteDelimiters` keep a backslash-preserving copy so escape decoding still has something to work on; the commit-message reader models git's actual short-option bundling.
- **Preventive rule / automated check:** Before shipping a guard that inspects a command string, write down every layer that transforms it between inspection and effect — shell quoting forms (`'...'`, `"..."`, `$'...'`, backslash), shell alias/function tables, the tool's own option grammar, and the invoked program's escape processing. Decode the ones you can and DECLARE the rest unread. When in doubt, scan the union of interpretations: over-approximating what you scan is safe, under-approximating is a bypass. And run the adversarial loop until the findings stop being routine — rounds 7, 8 and 9 each found a real defect that the previous round's fix had introduced.
- **Related files & tests:** `hooks/shell-quoting.mjs` (new), `hooks/codex-write-signal.mjs` (`stripQuoteDelimiters`, union push), `hooks/git-invocation.mjs` (`commitMessages`, `commitSweepsUnstaged`, `targetCwdsFor`), `hooks/scan-commit-names.mjs` (terminal-only `.pub`), `hooks/scan-commit.mjs`, `hooks/branch-guard.mjs`; `tests/test_secret_guard_bypasses.py::TestRoundFiveResiduals` through `::TestRoundNineResiduals`.

## 2026-08-23 — A new component must re-ask every question its neighbours already answered

- **Task / context:** Rounds 3 and 4 of an adversarial review loop over the guard fixes. Each round audited the previous round's output; the loop only stopped finding real defects after round 5.
- **Symptom:** Six further defects, and they share one shape. `hooks/git-invocation.mjs` was written as the new, correct way to decide "is this a git commit?" — and it independently re-lost capabilities the sibling guard `destructive-command-guard.mjs` had carried for months:
  - `(git commit -am x)` and `{ git commit -am x; }` were **completely invisible** (severity: critical). The first token is `(git`, whose basename is not `git`, so the resolver returned nothing and BOTH guards exited. The sibling guard has stripped subshell wrappers all along.
  - `git -C /tmp status; git commit -am '<token>'` redirected the COMMIT's diff read to `/tmp`, because every `-C` on the line was collected into one shared array instead of being scoped to the call that carried it.
  - `alias.ci = "commit -a"` meant `git ci` really swept unstaged tracked files, but the `-a` widening test still ran against the RAW typed string — the resolver's expansion was sitting one line away, already used for message scanning.
  - `cat <<-EOF > f` (tab-stripping heredoc) was neither read nor flagged, so `parsed:true` came back on an unread write — the third instance of the same CWE-636 shape in one work package.
  - `id_rsa.pub` was denied. The public half of a keypair is exactly what you are meant to commit; a guard that blocks routine safe work is the fastest way to get itself switched off.
- **Root cause:** Writing a focused new module makes it feel finished when it handles the case that motivated it. But a guard's real contract is the union of every evasion its neighbours already handle, plus every spelling of the operation it claims to recognize. Nothing in the codebase forced the new resolver to inherit the old one's wrapper stripping, and nothing forced the `-a`/heredoc/`.pub` paths to be re-derived from the new resolver instead of from the raw string.
- **Correct fix:** Strip group wrappers linearly before tokenizing; scope `-C` per statement and expose `targetCwdFor(info, subcommand, baseCwd)` so a consumer asks for the cwd of the call it actually cares about; test the RESOLVED texts everywhere the raw command was tested; accept `<<-` and mark any surviving `<<` as unread; carve `.pub` out of the credential-filename rule.
- **Preventive rule / automated check:** When you add a component that answers a question an existing component already answers, diff their capability lists before shipping — and port the old one's evasion handling deliberately, not by luck. When a fix introduces a resolver, grep the same file for every OTHER place that still tests the raw input the resolver was built to replace; those are the next bugs. And keep the adversarial loop running until a round comes back empty: rounds 2, 3 and 4 each found defects the previous round's fix had introduced, including one worse than anything in the original code.
- **Related files & tests:** `hooks/git-invocation.mjs` (`stripGroupWrappers`, per-statement `calls[]`, `targetCwdFor`), `hooks/scan-commit.mjs`, `hooks/branch-guard.mjs`, `hooks/codex-write-signal.mjs`, `hooks/scan-commit-names.mjs`; `tests/test_secret_guard_bypasses.py::TestRoundThreeResiduals`, `::TestRoundFourResiduals`.

## 2026-08-22 — Re-review the FIX: closing six bypasses introduced five more, one of them worse

- **Task / context:** After closing six verified fail-open bypasses in the PreToolUse guards, the same adversarial multi-lens review was pointed at the fix itself instead of at the original code.
- **Symptom:** Five real defects, all reproduced by execution. Ranked by what they teach:
  1. **The fix introduced a catastrophic ReDoS.** Supporting derived credential names added `(?:\.[A-Za-z0-9]{1,8}|~)*$` — an AMBIGUOUS REPEATED GROUP in front of an end anchor. Measured on `id_rsa` + `.a`xN + `!`: 459 ms at N=8, 1.16 s at N=10, **20.6 s at N=12**. A staged filename is agent-influenced, so the commit guard would blow past its 20 s budget and the runtime then fails open — the hardening became the bypass.
  2. **A cheap pre-filter silently undid the expensive resolver behind it.** Both guards gained `if (!/git/i.test(cmd)) exit;` in front of a new quote-aware tokenizer written precisely to handle `g'i't commit` — which contains no contiguous `git`, so the tokenizer never ran.
  3. Syntactic parsing without propagation: `-C <dir>` was parsed to find the subcommand but never passed to the git subprocesses, so alias lookup and `git diff` read the wrong repository.
  4. Resolution that discards its own intermediate result: the alias expansion was used to detect a commit and then thrown away, so a secret inside the ALIAS DEFINITION's `-m` was never scanned.
  5. A denylist extended for one spelling only: `UNREAD_WRITE` matched `sed -i` but not `sed --in-place`, restoring the parsed:true-on-an-unread-write shape the same commit claimed to have removed.
- **Root cause:** Each is the same failure at a different layer — a new component was added without re-asking the question the component was there to answer. The ReDoS specifically is the previously-recorded `/\s*\)$/` lesson in a new shape: the trap is not "greedy whitespace", it is **any ambiguous quantifier that can be split many ways sitting before an anchor that may fail**.
- **Correct fix:** Replace the suffix regex with a linear split-and-check function (20.6 s → 0.01 ms, flat across a 16x input range); strip quote/backslash delimiters before any cheap pre-filter so it can never be narrower than the resolver it guards; propagate `-C`/payload `cwd` into every git subprocess; return alias expansion TEXTS from the resolver and scan messages from all of them; cover both option spellings.
- **Preventive rule / automated check:** (a) A security fix is not done until the fix itself has been adversarially reviewed — the round that audits the patch found a worse defect than the round that audited the original. (b) Never place an ambiguous repeated group before an anchor in a scanner on agent-influenced input; measure at 8/10/12 repetitions before shipping, because the curve is invisible at small N. (c) A cheap pre-filter in front of a precise resolver must be a strict SUPERSET of it. (d) If you parse an option to make a decision, propagate it to every side effect that decision drives.
- **Related files & tests:** `hooks/scan-commit-names.mjs` (new, linear), `hooks/git-invocation.mjs` (`resolveGitCommands`, per-call alias-lookup cwd), `hooks/scan-commit.mjs`, `hooks/branch-guard.mjs`, `hooks/codex-write-signal.mjs`; `tests/test_secret_guard_bypasses.py::TestFixResiduals`.

## 2026-08-22 — A recognition flag must default to FALSE ("I parsed it" vs "I saw no `$`")

- **Task / context:** Closing a fail-open in `hooks/codex-write-signal.mjs`, the pure write-content extractor behind the Codex pre-write secret guard.
- **Symptom:** `echo "" <github-token> > notes.txt` reached the guard as `addedContent: ""`, `targets: ["notes.txt"]`, **`parsed: true`** — the guard scanned an empty string, allowed the write, and the shell wrote the token to disk. The same `parsed: true` came back for `tee`, `dd`, `sed -i`, `cp`, `>|` and `&>` — every form the file's own header comment claimed was reported `parsed:false`.
- **Root cause:** Two independent optimistic defaults. (1) `parsed` was computed as `!hasExpansion`, and `hasExpansion` was set on only two code paths, so it meant "I saw no `$` or backtick", never "I accounted for this command"; every "I do not recognize this form" path was a bare `continue` that left the flag true. (2) `extractLiteral()` returned only the text between the FIRST pair of quotes (or a bare word with no whitespace) and dropped the rest of the payload, so a multi-token `echo`/`printf` argument list was silently truncated. This is OWASP "fail securely" / CWE-636: an optimistic initial value that survives every path that failed to disprove it.
- **Correct fix:** Under-approximate RECOGNITION and over-approximate CONTENT — they must go in opposite directions. `parsed` now starts from an explicit `unreadWrite = false` that any unrecognized write form flips; the payload scanner reads the WHOLE argument list (quote delimiters stripped) instead of its first literal token, because the byte set scanned must be a superset of what lands on disk while the DENY decision stays exact (a HIGH pattern is a vendor-shaped token that neighbouring text cannot manufacture).
- **Preventive rule / automated check:** In any scanner or guard, a flag that answers "did I understand this input?" is initialised to the unsafe-to-assume value (`false`) and set true only on the specific paths that produced a complete reading; never derive it from the absence of one particular hazard. Assert it: a test must show that a payload the extractor drops cannot also come back with the flag set (`test_parser_never_claims_parsed_while_dropping_payload`).
- **Related files & tests:** `hooks/codex-write-signal.mjs` (`parseBash`, `payloadText`, `UNREAD_WRITE`); `tests/test_secret_guard_bypasses.py::TestCodexWriteLiteralTruncation`.

## 2026-08-22 — Never apply a "probably not real" heuristic to a value that already passed a structural test

- **Task / context:** Closing a false-negative class in `hooks/secret-patterns.mjs`, the shared secret scanner used by both runtimes' commit and write guards.
- **Symptom:** Verified by execution (agentic-sdlc:allow-secret) — `sk_test_xxxx…`, `ghp_xxxx…`, `password=MyRealSecretExample8412`, and a JSON credential value containing a single `<` were all reported clean and committed unblocked.
- **Root cause:** One unanchored substring regex (`…|example|x{4,}|\$\{|<|>|…`) was applied to whatever the pattern matched. Nine of the eleven HIGH patterns carry no `valueGroup`, so the "value" it inspected was the ENTIRE vendor-shaped token — one that had already passed a strict, vendor-published shape test. A placeholder heuristic designed for a user-authored right-hand side was silently deciding the fate of issued credentials.
- **Correct fix:** Route by pattern KIND. Captured (user-authored) values keep the heuristic, but as ANCHORED whole-value predicates (`^<…>$`, `^\$\{…\}$`, `^process\.env`) instead of substring probes. Vendor-shaped tokens are never keyword-filtered: they are suppressed only when structurally degenerate (one character dominating, or a monotonic run — the pattern filter from Meli et al., NDSS 2019) or when they match a published doc sample EXACTLY. This is what the mature scanners do: gitleaks attaches its stopword list only to the generic rule and gates vendor rules on entropy; detect-secrets hard-disables its context heuristic for regex-based detectors; trufflehog applies keyword filtering only to results it could not verify as live.
- **Preventive rule / automated check:** A suppression rule must be scoped to the detector it was designed for, and stated as an anchored predicate over the whole value — a substring probe in a security filter suppresses a class, not an instance. Any new suppression needs a paired test: the bypass it must NOT create, and the false positive it must still prevent.
- **Related files & tests:** `hooks/secret-patterns.mjs` (`TEMPLATE_VALUE`, `DOC_SAMPLES`, `isDegenerateToken`, `scanLines`); `tests/test_secret_guard_bypasses.py::TestPlaceholderFilterOnVendorTokens`, `::TestTokenBoundaryAnchoring`.

## 2026-08-22 — A guard gated on a raw command substring is defeated by aliasing; a narrowing wiring filter disables it outright

- **Task / context:** Closing two bypasses of `hooks/scan-commit.mjs` and `hooks/branch-guard.mjs`.
- **Symptom:** `git config alias.ci 'commit -a'` followed by `git ci -m x` performed a real commit — sweeping unstaged changes — with both guards completely silent. Separately, on a Windows host without Git Bash no command guard fires at all.

(2) `hooks/hooks-claude.json` narrowed the hooks with `"if": "Bash(git commit*)"`, so for `git ci` the hook PROCESS never started and no internal fix could have helped — and the runtime documents `if` as best-effort, recommending the permission system for a hard allow/deny. (3) `matcher: "Bash"` — Claude Code does not register the Bash tool on Windows without Git Bash, so a Bash-only matcher is inert there.
- **Correct fix:** Move the decision into the guard and make it resolve what git will ACTUALLY run: `hooks/git-invocation.mjs` expands git aliases the way git does (chains, `!shell` aliases, `-c alias.x=y`), skipping global options and wrappers, over a quote-aware tokenizer. ## 2026-07-01 — A greedy `\s*`/`\s+` before a `$` end-anchor is O(n²) (ReDoS in command parsers)

- **Task / context:** B5 (#5) closing the Codex flow-order write-form bypass — new `preciseWriteTargetsOf` in `hooks/codex-rollout.mjs` re-implemented a subshell-strip helper as `seg.trim().replace(/^\(\s*/, '').replace(/\s*\)$/, '')`, mirroring the existing `parseBash` in `hooks/codex-write-signal.mjs`.
- **Symptom:** Security review measured the strip at ~1.1 s (40 KiB) → ~4.3 s (80 KiB) → ~17.6 s (160 KiB) on `"echo" + " ".repeat(N) + "x"` — a clean 4×-per-2× quadratic. At the 512 KiB command cap that hangs the PreToolUse hook for minutes; under `AGENTIC_FLOW_ORDER_BLOCK` the timeout then fail-opens → the hardening becomes a self-inflicted DoS/bypass. Triggered by ANY long internal whitespace run with no trailing `)` (not just a write).
- **Root cause:** `/\s*\)$/` is unanchored at the start, so the engine retries from every index in the whitespace run; each retry's greedy `\s*` scans to end then backtracks to find the required `)`+`$` — O(n) work × O(n) start positions = O(n²). The `$`-anchored greedy-whitespace shape is the trap, independent of the `g` flag.
- **Correct fix:** Replace with linear string ops — `trim()`, then single-char `slice` for a leading `(` / trailing `)`, then `trim()` again. No regex with a start-unanchored greedy `\s*` before `$`.
- **Preventive rule / automated check:** Never put a greedy `\s*`/`\s+` (or `[\s\S]*`) immediately before a `$` end-anchor in a scanner that runs on attacker/agent-influenced input; prefer `trim()`/two-pointer strips. A "linear (BR10)" claim in a comment is not evidence — add a timing regression test on a long internal-whitespace input (see `test_precise_scan_linear_internal_whitespace`). **Known residual:** the identical twin at `hooks/codex-write-signal.mjs:69` (`parseBash`) is byte-locked and pre-existing; it is reachable by default via the always-on `scan-write-codex.mjs` secret guard on every Bash command — a separate follow-up (needs a byte-lock rebaseline), not fixed in #5.
- **Related files & tests:** `hooks/codex-rollout.mjs` (`stripWrappingSubshell`); `tests/test_codex_flow_order_guard.py` (`test_precise_scan_linear_internal_whitespace`, `test_precise_scan_linear`, `test_raw_scan_linear_flood`).
